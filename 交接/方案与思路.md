## 一、owner 要的是什么（从 559 条 owner 消息归纳）

1. **定位：通用 Agent 底座，不是编程 IDE。**
   - 不同的工作做成一个个套件，每个项目按需加载套件和右侧工具栏。
   - 软件里大量设计目前只考虑了编码，需要能承载生图、生视频、文档等非编码工作。
2. **底座用 ZCode，并做到：**
   - 去掉品牌标识、官方服务器连接、数据收集、升级套餐等商业化设计；
   - 账号区参考 OpenChamber 的 GitHub 集成，或像 Cherry Studio 那样可以自己改名字和头像；
   - 保留原版有用的功能弹窗、快捷键和说明文字。
3. **从 Craft 留下的是交互，不是前端：**
   - 在任何功能页右键（或点按钮）就地唤出小对话框，把该页面的文档和操作目标交给 Agent。重点是 Agent 需要什么上下文，而不是用户想做什么；
   - 对话气泡的设计；
   - 看板，与 dashi-taskboard 结合做成插件；
   - 本地化的帮助文档，主要给 Agent 读。
4. **Agent 能操作软件的全部功能。** 人的按钮、页面小对话、主对话里的 Agent，调用的是同一个功能操作。
5. **项目就是文件夹。** 对话放在文件夹里；不选文件夹就是普通对话或任务。不再分会话、工作区、项目三层。
6. **模型是地基，要最先做好：**
   - **接入：** 按厂商分组，同一厂商的订阅和 API 分开；同一种方式可以绑多个密钥或账号，有同厂商、同模型的自动切换开关；要防止请求死循环、反复重试已失效的账号，并规避封号风险。
   - **模型列表：** 自动拉取，识别到的模型直接可用，可以手动补充或纠正，每个模型有开关。
   - **能力标签：** 先显示上下文；普通对话模型不加标签；功能标签包括图片生成、视频生成、语音识别、OCR、视觉/视频/音频输入、文件（文件标签不给非对话模型）。思考强度不放进标签。语音输入将来做成插件。
   - **订阅信息：** 额度、会员档位（不同档位不同颜色的小标签）、剩余天数、重置卡（要能在软件里直接使用）。额度信息人和 Agent 都要能看到。
   - **API 格式：** 用上游格式；不要让用户纠结选哪种，界面上解释清楚差别即可。
   - **支持范围要广：** ChatGPT、Claude、Grok（订阅和 xAI API 的名称、图标要分开）、Antigravity、Gemini、Kimi、Qwen、GLM、DeepSeek、MiniMax 等；能导入 CC Switch 里的配置（自动勾选可用项，去重）。
   - **生图、生视频、生音频模型：** 要能被对话 Agent 调用，产出能预览，并能和对话模型配合。
7. **输入框：**
   - 学 Codex 桌面版：模型和思考强度合在一个入口，快速模式做成小闪电（每家的加速倍率要查清楚并计入统计），窗口变窄时收成大脑图标；
   - 只有可选上下文的模型才显示上下文选择，首次对话前就要知道上下文上限；
   - 新建对话有默认模型，项目里的新对话沿用该项目上次用的模型；
   - 拖入文件能小窗预览各种格式。
8. **Token 环和用量统计：**
   - Token 环保持 ZCode 原版的设计；显示当前对话所用模型对应的账号；
   - 统计页显示每个模型的缓存命中率、按官方价格估算的花费、订阅和 API 原价的直观对比（不需要精确记账；订阅价可以手动纠正）、每个项目的花费（没归到项目的算"其他"）、工具和技能的调用次数；
   - 这些数据是给 Agent 用来控制成本、决定插件和技能去留的，统计页也要有 Agent 可以编辑的地方。
9. **模型侧轻量：** 功能可以很多，但模型看到的上下文要像 Pi 一样精简。
10. **非编码产出：** 生图、生视频、文档类任务要有自己的结果入口，不能只靠代码变更弹窗。
11. **其他基础能力：**
    - 内置真实浏览器，能装 Chrome 插件；
    - 文档预览（参考 Craft 和 LobeHub）；
    - IM 机器人（参考 Cindy 的 IM 和 ZCode 的 Bot Channel）；
    - 支持 Windows、Mac、Linux，后续做手机连接（参考 Orca）。
12. **插件（等底座做好之后）：**
    - 兼容主流插件格式；插件可以增加页面和右侧工具；
    - Agent 能为软件写插件，也能把独立的开源项目改造成插件（参考 Cindy 移植 Open Design）；
    - ZCode 原版的 PDF、演示文稿、表格、Word 插件和技能，结合 GenOffice 做成办公套件；
    - 插件市场要能容纳庞大的生态。
13. **工作方式：**
    - 每个模块动手前，先看官方软件、插件生态和几个开源项目的前后端源码，能搬就搬，只改字体、字号、颜色、圆角、阴影来统一风格；
    - 不靠截图判断，不自己发明交互，不把两套 UI 拼在一起；
    - 修改要和原版对比，确认是在改进而不是越改越差；不要过度工程化；
    - 按最大功能闭环提交；
    - 给 owner 验收之前自己先验收，打开软件告诉他改了什么、要验收什么；
    - 不做无意义的阶段汇报；重要信息写进文档；
    - 能分支的工作就多 Agent 并行，并交叉审查；
    - 做出来的东西要超越参考项目。

## 二、CLI 接入方案（owner 当前最关心的核心问题）

### 2.1 结论

几个参考项目最后用的都是同一套分层，我建议照 Paseo 的结构实现：

1. **有官方结构化接口的，走官方接口：**
   - Claude Code：Agent SDK 或 stream-json。候选版已经有原生 Claude 通道，复用它；
   - Codex：`codex app-server --stdio`（JSON-RPC，需要回应服务端发来的反向请求）；
   - Antigravity：官方 `agy` 程序（每轮一个进程，用 `--conversation <id>` 接续）。
2. **其余 CLI 统一走 ACP：** Gemini CLI、Qwen Code、Kimi、OpenCode、Hermes、Cursor、Copilot、Kiro 等。
3. **不做 PTY 终端兜底。** Orca 有这一层，但我们不是终端产品。
4. **每个 CLI 写成一个"执行后端插件"，并声明能力。** 能力参考 Paseo `provider.ts:7-23`：发图、中途插话、回退、会话持久化、权限策略等。界面只显示该后端真正支持的功能，不支持的直接隐藏或说明。插件市场以后也能新增 CLI。

### 2.2 CLI 自带的驾驭工程和 Skills

- **驾驭工程整体保留。** 不在外面再套我们自己的模型或工具循环。现有规则已经禁止这种做法，继续遵守。
- **我们的 Skills 怎么交给 CLI：**
  - CLI 有原生技能目录的，就把技能链接进对应目录（照 AionCore 的 `native_skills_dirs` 表，并按各家官方文档核对路径；Codex 应为 `.agents/skills`）；
  - 没有原生目录的，在首条消息注入技能目录；
  - 各家热加载能力不同：Claude 能在会话中途识别；Gemini 要执行 `/skills reload`；Qwen 必须重启。界面要如实显示"新技能下个会话才生效"。
- **MCP：** 在创建会话时传入（ACP 的 `session/new` 本身支持）。
- **让 CLI 也能操作我们的软件：** 把页面和功能操作做成一个 MCP 服务，注入 CLI 会话，每个后端可以单独限制可用工具（照 Paseo 的 `paseoTools`）。这和第一节第 4 条是同一个功能操作层。

### 2.3 CLI 里跑非官方模型（核心问题）

原则：**模型跟着自己的驾驭工程走。** 分三种情况：

| 情况 | 例子 | 做法 |
|---|---|---|
| 厂商提供兼容端点 | Z.AI、Qwen、Kimi、MiniMax 的 Anthropic 兼容端点 | 做"继承 Claude 的档案"：环境变量写 `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`；关闭第三方端点不支持的服务端工具（如 WebSearch）；填写该厂商的模型列表。用量、价格、额度都记到**实际模型和账号**（例如 GLM），不能记成 Claude |
| 端点不兼容 | OpenAI、Gemini、xAI | **不默认**用 NewMax 那种转换代理硬塞进 Claude Code。Claude Code 的提示词和工具是为 Claude 调的，换成 GPT 跑会丢掉官方的驾驭优化，而这恰恰是 owner 想要的效果。这类模型应走自家 CLI（GPT 用 Codex，Gemini 用 agy 或 Gemini CLI），或者走我们自己的 Pi 通道。转换代理最多作为高级选项，并明确标注"非原生" |
| 订阅账号 | Claude、ChatGPT、Antigravity 会员 | 只通过官方 CLI 自己的登录。不采用 NewMax 那种伪装官方客户端的做法，有封号风险 |

**界面上的要求：** 每个会话都要显示"驾驭工程 + 模型 + 账号"三项，这样用量统计和额度才能归到正确的地方。

### 2.4 支持哪些 CLI

- **内置：** Claude Code、Codex、Antigravity，加上通用 ACP。
- **按需安装（插件）：** 其余 CLI。
- **动手前要先读：**
  - Grok Build 怎么接入（`源码参考/software/grok-build`）；
  - Orca 的 `src/main/antigravity`；
  - AionCore 的 `antigravity/conn.rs`；
  - 实测 agy 是否支持图片输入。

### 2.5 需要 owner 拍板

**Antigravity 的接法：**
- A. 走官方 agy CLI（推荐）：合规，Paseo 和 AionCore 都这样做；
- B. 照 NewMax 自己做账号登录：能力更全，但有封号风险。

## 三、开发顺序（建议），每步都写明完成标准

顺序和 owner 说过的一致：先地基，再基础功能，最后插件。

### 第 1 步：模型地基补完（当前最高优先级）

- **要补的缺口：**
  - ChatGPT 登录后状态不对；
  - Claude 订阅：额度为空的原因要查清；
  - Grok 快速模式；
  - Antigravity（等 owner 拍板）；
  - CLI 通道：按第二节实现，至少 Codex app-server、agy、通用 ACP；
  - 新建对话的默认模型，以及项目里沿用上次的模型；
  - 输入框的模型、思考强度、快速模式、上下文选择（照 Codex 桌面版）；
  - 生图、生视频、生音频的完整链路：从对话调用 → 生成文件 → 预览，再到用量记录；
  - CC Switch 导入：自动勾选可导入项，去重，测试连通性，状态要真实。
- **完成标准：** 每个声称支持的厂商和账号都要用真实路径跑通，并在内置浏览器或打包后的应用里亲自验收。只有配置界面不算支持。
- **停止条件：** 同一个方法试两次仍然不行，就停下记录现象，换最小的替代方案，或者把决策交给 owner。

### 第 2 步：模型侧轻量化

- 先测量：普通对话时的系统提示词和工具说明各有多少 token。
- 再定一个上限，用 NewMax 的"按需搜索工具"或 Pi 式的小工具集达到它。
- 完成标准：任务效果不下降（用固定的一组任务对比），上下文降到上限以内。
- 同时把文档里"完整 Pi"的说法改成真实描述。

### 第 3 步：统一的功能操作层，加上页面 Agent

- 每个功能的操作只定义一次，带权限、版本检查和撤销，同时暴露成：按钮、右键小对话（照 Craft 的 `EDIT_CONFIGS`）、主对话里的工具、给 CLI 的 MCP 服务。
- 从设置类页面开始逐页铺开：模型、插件、MCP、技能、权限、项目设置、用量统计。
- 完成标准：每个页面都能右键唤起，并带上正确的目标和文档；Agent 改完后原页面会刷新；人正在编辑的草稿不会被覆盖。

### 第 4 步：非编码产出视图和其他基础功能

- 接着 Codex 正在做的工作，让生成的文件进入结果入口，重新打开历史记录时附件不丢。
- 输入框文件预览、文档预览。
- 内置浏览器：真实 Chromium，能装 Chrome 插件。先看 Codex 桌面版的浏览器是怎么实现的。

### 第 5 步：插件框架

- 给插件加页面和右侧工具的扩展点。把写死的右侧面板类型改成可以注册的（参考 Cindy 的 `registerTabKind`）。
- 兼容 `.claude-plugin`、`.codex-plugin` 和 ZCode 格式（导入器已经支持）。
- 第一个插件做看板（dashi-taskboard 的 HTTP API 加 `taskctl`），验证"人和 Agent 改的是同一份数据"，以及安装、禁用、重启、卸载都不丢数据。

### 第 6 步：套件和远程能力

- 办公套件：ZCode 原版插件加 GenOffice。
- 画布：用 React Flow，不用 tldraw。
- 媒体工作流、IM 机器人、手机连接、跨平台打包。
