# 02 · Codex 方案评审

> 评审对象：`AGENTS.md` + `docs/Fleet-*.md` + `docs/源码*.md` + `docs/craft-base-prep.md`。
> 评审方法：逐份通读 + 对照我对 `源码参考/craft-agents-oss`、`AionUi` 的源码实测做事实核对。

## 总评

**质量高、事实准、可直接执行。** 我核对的具体声明都成立：craft 数据目录 `~/.craft-agent`、协议 `craftagents://`、产品名 `craft-agent`（所以"去 Craft 化"清单是对的）；AionUi 确有 **ACP + team**（所以那条迁移路径是真的）；`craft-base-prep` 记录的 typecheck+build 通过也属实。许可证治理、"不引入第二套会话系统"、多智能体审查协议都是成熟判断。下面分三块：**务必保留 / 必须补 / 能更好**。

---

## 一、做得对，务必保留（迭代中别丢）

1. **基座纪律**：craft 主 + AionUi 第二绿灯，其余黑盒；红绿灯表 + 迁移归因台账 + BSL/AGPL/非商用标注 —— 想商业化，这是护身符。
2. **"不得引入第二套会话系统，AionUi 适配进 craft 的 `SessionManager`/`SessionEvent`"** —— 融合两套代码**最关键**的纪律。很多团队会把 AionUi 的 session 系统并排塞进来搞成两套真相；Codex 抓住了。
3. **CLI Runtime Host 的 P0-B 探测边界**（白名单、只 `--version`、超时、无 stdin、固定 cwd、不读 token、不改配置、输出截断）—— 教科书级安全卫生。
4. **多智能体"先审查后并行 + 证据链 + 确认门"** —— 把你的"队长→小队"愿景落成了可执行协议（含 per-agent 身份、权限分组、回滚）。
5. **RPC locality（LOCAL_ONLY / REMOTE_ELIGIBLE）+ 多 Agent 身份元数据 + 权限/回放统一** —— 正确的底层约束。

---

## 二、必须补的缺口（按重要性）

### G1（最重要）· 没有评测 + 可观测 → 进不了"世界顶尖"
实测：craft **只有单元测试，没有 agent 评测/回归/打分框架，也没有追踪/回放/成本的产品面**。Codex 路线是"功能补齐"导向——每个能力有 DoD，但 DoD 是**单点验收**，不是**可度量的任务成功率**。顶尖 Agent 工具的护城河恰恰是"可度量的可靠性 + 出问题能回放"。
**建议**：把 **Eval & Observability 作为贯穿 P0→P2 的独立工作流**早早起步（至少 P1 先搭骨架）：①任务集 + 成功率 + 回归门禁；②步级 trace + 回放 + 成本/延迟仪表盘。**不要拖到 P2。**

### G2 · 硬分叉 vs 软分叉没定，而"去 Craft 化"会替你做决定
`AGENTS.md` 规则 6 说"先别大改、保持 craft 能跑"，但路线又把"去 Craft 化"（改包名、`craftagents://`、`~/.craft-agent`、产品名、全量英→中）放得很靠前。**全量改名 = 事实上的硬分叉**——之后再想合并 craft 上游（它还在 0.10.x 活跃更新、有 `next.md`）会非常痛。
**建议**：明确二选一。要么承认**硬分叉**（自由改名、放弃上游）；要么**软分叉**（核心包名/协议先不动，品牌只做在**用户可见层** + 你的增量放**独立 package**，定期合上游）。小团队 + craft 活跃 → 我偏向**软分叉**，把深度"去 Craft 化"压到你确定不要上游之后。先写半页 **分叉策略 ADR**。

### G3 · "CLI Runtime Host 当第一个建的东西"与"新手护城河"有排序张力
craft + Claude Agent SDK + Pi 已能在**进程内**给到 Claude Code 级能力。托管**外部 CLI** 的独特价值是复用用户已有的 CLI 订阅/鉴权——这偏 **power-user**；而你的北极星是**新手 / 低摩擦**（新手电脑上根本没装 Codex CLI）。
- P0-B 探测便宜安全，做无妨；
- 但投入 P0-C 全量"启动 + PTY + 会话"之前，先掂量：**是不是该把"新手群聊编排"这个差异化排到 CLI 托管之前？**
- Codex 已写对"优先 ACP/SDK/MCP，PTY 兜底"——**强调走 ACP**（AionUi 已有，是新兴标准），别去 PTY 抓屏解析 CLI（脆、难维护）。

### G4 · "先做底层、不改 UI"有返工风险
底层 RPC/service 若照 craft **当前**信息架构设计，等 P2 重排首屏时可能要改形状。
**建议**：先做一次**可丢弃的首屏 spike**（哪怕假数据），校准目标 IA，让底层 RPC 按**目标 UX** 长，而不是按 craft 现状长。Codex 已提"P0 结果要能被 P2 复用"，spike 是落实它的最便宜手段。

## 三、世界顶尖还要加的（Codex 没列，实测 craft 也没有）

| 能力 | craft 现状（实测） | 为什么顶尖必备 |
|---|---|---|
| 计算机使用 / 更强浏览器自动化 | 有 browser CDP，**无 computer-use（截屏/点击/视觉）** | 前沿工具都在抢"操作任意软件" |
| 容器级沙箱 | 有进程级 fs/网络隔离 + `script-sandbox`，**无 Docker/microVM** | 给普通人放手跑不可信代码的安全底线 |
| 语音 / 多模态输入 | **无 agent 语音** | 新手最自然的入口之一 |
| 跨会话记忆 / 检索 | 有压缩打底，记忆/检索弱 | 长期个人化体验；Codex 放 P2，保持在图上即可 |

## 四、小确认 / 纠正点

- 数据目录/协议/品牌名 Codex 写得准（核过：`.craft-agent`×183、`craftagents://`×50、product `craft-agent`）。改名时给老数据目录留**兼容层**（Codex 已想到 `~/.fleet` vs 兼容）。
- 迁移台账已 pin craft commit `a512da7` ✓；**开始迁 AionUi 时同样要 pin AionUi commit**。
- "DeepSeek/智谱/Qwen/Ollama 低摩擦入口"列在 P2——注意 craft **已支持**这些（openai-compat + 各家），所以是"做默认/模板化/向导"，**不是"加支持"**，工作量比想象小。
- 企业微信/钉钉列 P2 ✓——craft 的 `messaging-gateway` 已有 **lark + telegram adapter** 干净范式，照着写新 adapter 即可（这点比 Codex 文档里说得还乐观）。

## 五、建议的修订动作（最小改动，最大收益）

1. 路线里加一条**贯穿 P0→P2 的 Eval & Observability 工作流**（G1）。
2. 写半页**分叉策略 ADR**（硬/软分叉二选一），据此重排"去 Craft 化"时机（G2）。
3. P0 加一个**一次性首屏 spike**，校准底层 RPC 形状（G4）。
4. 缺口表补 **computer-use / 容器沙箱 / 语音** 作为 P2/P3 顶尖线（第三块）。
5. CLI Host 维持 P0-B 探测；**P0-C 之前与"新手群聊编排"做一次优先级对比再定序**（G3）。

> 一句话：Codex 的方案**底子很稳、可以直接照着干**；要冲"世界顶尖"，主要补 **可度量的可靠性（评测+可观测）**，并**想清楚分叉策略**——这两点定了，剩下按它的阶段推进即可。
