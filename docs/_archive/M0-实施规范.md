## 1 · 与 v2 的关系（定调）

**v3 新开 `app/` 目录，独立工程，不动 `v2/`。**
- `v2/` 是 pi-tui 薄客户端路线，**冻结**，不在其中加 GUI。
- `app/` 是全新的 Electron+React 桌面工程，从 v2 **复用资产/模式**（见 §11），但不反向依赖 v2 源码。
- 两者可长期共存：v2 仍是 OmniVerse 后端的 TUI 消费者；`app/` 是面向新手的桌面编排壳。

## 2 · M0 做什么（精确范围）

只做这 7 件，**做完即 M0 完成**：

1. **Electron 桌面壳**：单窗口，electron-vite 起步，能在 Mac/Win 启动。
2. **React 聊天界面**：输入框 + 流式消息 + 左侧 Agent 状态 + 设置页 + 失败态。
3. **内置 Pi Agent 子进程**：独立 Node 进程，JSONL over stdio，跑 `pi-agent-core` 循环。
4. **BYO key / Ollama 配置**：首启向导选工作区 + 配模型；只支持 OpenAI-compatible 与 Ollama 两种。
5. **最小 EventStream**：§6 的 9 类事件，内存 + 按会话 JSONL 落盘。
6. **最小安全工具**：`fs.list`、`fs.read`、受控 `shell.run`（内部工具注册表，非 MCP）。
7. **审批弹窗**：`shell.run`（及任何 `risk:"approval"` 工具）执行前必须用户确认。

## 5 · 进程通信协议

三个进程：**main（受信任）↔ renderer（无 Node）↔ agent 子进程（受限，不碰 fs/shell）**。
**关键安全设计：工具在 main 执行，不在子进程执行。** 子进程只"请求"工具，main 审批+执行+回结果。

### 5.1 renderer ↔ main：ipc（contextBridge + invoke/push）

preload 暴露 `window.fleet`，全部经 `shared/ipc-contract.ts` 校验。

```ts
// 请求/响应：renderer 调 window.fleet.X → ipcRenderer.invoke → ipcMain.handle
"chat:send"          {sessionId?: string, text: string}            -> {sessionId, runId}
"agent:cancel"       {runId: string}                               -> {ok: boolean}
"approval:respond"   {toolCallId, decision:"approve"|"reject",
                      remember?: boolean}                          -> {ok: boolean}
"config:get"         {}                                            -> ResolvedConfig // key 已脱敏
"config:set"         {patch: Partial<ModelConfig & Settings>}      -> {ok: boolean}
"workspace:pick"     {}                                            -> {root: string}
"session:events"     {sessionId: string}                           -> FleetEvent[]

// 推送：main → renderer，webContents.send → ipcRenderer.on
"event"              FleetEvent                  // EventStream 实时投影
"approval:request"   {toolCallId, runId, tool, args, risk}         // 弹审批
```

`preload/index.ts` 只暴露上述白名单方法 + `onEvent(cb)`、`onApprovalRequest(cb)`；renderer 无法直接 `require('fs')`。

### 5.2 main ↔ agent 子进程：JSONL over stdio

`child_process.spawn(node, [subprocessEntry], { stdio: ['pipe','pipe','pipe'] })`。
**stdout = 协议（每行一个 JSON），stderr = 日志，stdin = 指令。** 每条消息带 `v:1`。

```ts
// main → agent (写 stdin)
{v:1, type:"run", runId, sessionId,
   messages: {role:"user"|"assistant"|"system", text:string}[],
   modelConfig: {providerKind, baseUrl, model, temperature?},   // 不含 key
   toolSpecs: {name, description, parameters /*TypeBox JSON*/}[]}
{v:1, type:"cancel", runId}
{v:1, type:"tool.result", toolCallId, ok, result?, error?}      // 回应 agent 的 tool.call

// agent → main (写 stdout)
{v:1, type:"ready"}
{v:1, type:"event", event: FleetEvent}                          // 透传 EventStream 事件
{v:1, type:"tool.call", toolCallId, runId, name, args}          // 请求 main 审批+执行
{v:1, type:"token", runId, delta:string}                        // 流式增量（可选，驱动打字机）
```

- **API key 不走协议**：在 `spawn` 时通过 **env** 注入（`env:{...process.env, FLEET_API_KEY}`），不进 JSONL、不落日志。
- pi 的 `AgentTool.execute(toolCallId, params, signal)` 在 `tool-proxy.ts` 里实现为：发 `tool.call` → 挂起 Promise（键 `toolCallId`）→ 收到 `tool.result` 后 resolve；`signal` abort 时 reject 并发 `cancel`。

### 5.3 错误 / 取消 / 重试

```ts
// shared/errors.ts
FleetError = { code: ErrorCode, message: string, retryable: boolean, cancelled: boolean }
ErrorCode = "model_error" | "network_error" | "timeout" | "tool_error"
          | "rejected_by_user" | "cancelled" | "protocol_error" | "spawn_error"
```

- **错误**：任何失败都归一成 `FleetError`。模型/网络错→`agent.failed{error}`；工具错→`tool.completed{ok:false,error}`（模型可继续应对）。
- **取消**：renderer `agent:cancel` → main 发 `cancel` → 子进程 abort 模型调用的 `AbortController` + reject 所有挂起 tool-proxy → 发 `agent.failed{cancelled:true}`。**兜底**：main 若 1.5s 内未收到子进程 ack，`kill` 并重启（`spawn_error` 不影响其他会话）。
- **重试**：M0 **仅手动重试**（失败态有「重试」按钮 → main 用同样 messages 重发 `run`）。`network_error`/`timeout` 可选自动重试 ≤2 次（带退避）；其余不自动重试。

## 6 · EventStream 最小 schema

`shared/events.ts`，zod 可辨识联合。所有事件含基字段 `{v:1, id, ts, sessionId}`。

```ts
session.created   { type, ...base, cwd: string, title?: string }
message.added     { type, ...base, messageId, role:"user"|"assistant"|"system", text }
agent.started     { type, ...base, runId, agentId, model: string }
tool.requested    { type, ...base, runId, toolCallId, tool: string, args: unknown,
                    risk:"safe"|"approval" }
tool.approved     { type, ...base, toolCallId, by:"user"|"auto" }
tool.rejected     { type, ...base, toolCallId, reason?: string }
tool.completed    { type, ...base, toolCallId, ok: boolean,
                    result?: unknown, error?: {code,message}, durationMs: number }
agent.completed   { type, ...base, runId, usage?: {inputTokens?, outputTokens?} }
agent.failed      { type, ...base, runId, error: {code,message}, cancelled: boolean }

FleetEvent = discriminatedUnion("type", [...上述 9 个])
```

- **存储（M0）**：`event-store.ts` 维护内存数组 + 追加写 `.fleet/sessions/<sessionId>.jsonl`（一行一事件）。`replay(sessionId)` 读回；`subscribe(cb)` 给 main 转推 renderer。
- **UI 即事件投影**：renderer 不维护独立真相，`chat-store` 只把 `FleetEvent` 流投影成消息/工具卡片/状态。
- **审批闭环**：`tool.requested(risk:"approval")` → 弹窗 → `tool.approved`/`tool.rejected` → 执行 → `tool.completed`。`risk:"safe"` 的工具直接 `tool.approved{by:"auto"}` 不弹窗。

## 7 · 工具层：内部注册表（接口可迁 MCP）

M0 **不做 MCP**，做一个内部注册表，但接口**刻意对齐 MCP 工具形状**（name/description/inputSchema/handler），M1 可整体替换为 MCP client 而不动调用方。

```ts
// shared/tools.ts
export interface ToolSpec<P=any, R=any> {
  name: string;                 // "fs.list" | "fs.read" | "shell.run"
  description: string;
  parameters: TSchema;          // TypeBox（与 pi AgentTool.parameters 同源；= MCP inputSchema）
  risk: "safe" | "approval";
  run(args: P, ctx: ToolContext): Promise<ToolResult<R>>;
}
export interface ToolContext { workspaceRoot: string; sessionId: string; signal: AbortSignal; }
export type ToolResult<R=any> =
  | { ok: true;  result: R }
  | { ok: false; error: { code: string; message: string } };
```

`registry.ts`：`Map<string, ToolSpec>`，M0 注册三个。main 收到子进程 `tool.call` → 查注册表 → 判 `risk` → （需要则审批）→ `run(args, ctx)` → 回 `tool.result` + 发 `tool.completed`。

| 工具 | 入参 | risk | 行为 |
|---|---|---|---|
| `fs.list` | `{path:string}` | safe | 列目录（限工作区内）；返回名称/类型/大小 |
| `fs.read` | `{path:string, maxBytes?:number}` | safe | 读文件（限工作区内，默认 ≤256KB，超限截断标注） |
| `shell.run` | `{command:string, cwd?:string}` | **approval** | 工作区内执行，超时 60s，输出截断 64KB，cancel 即 kill |

> **迁移点**：M1 把 `registry.run` 换成「MCP client 调用本地 MCP server」，`ToolSpec` 几乎 1:1 映射 MCP tool；审批逻辑升级为 MCP approval gate。

## 8 · 模型配置（M0 只两类）

```ts
// shared/config.ts
export type ProviderKind = "openai-compat" | "ollama";
export interface ModelConfig {
  providerKind: ProviderKind;
  baseUrl: string;
  model: string;
  apiKeyRef?: string;      // 指向 secrets 存储的 id，不是明文 key
  temperature?: number;
}
```

- **只实现两类 provider 逻辑**：`openai-compat`（OpenAI 风格 `/chat/completions`）与 `ollama`。
- **DeepSeek / Qwen / 智谱 / OpenAI 只是预填模板**（baseUrl+model 预设，全部走 `openai-compat`，**不单独写 provider 代码**）：

| 模板 | providerKind | baseUrl（示例，以官方文档为准） | model 示例 |
|---|---|---|---|
| DeepSeek | openai-compat | `https://api.deepseek.com/v1` | `deepseek-chat` |
| Qwen（百炼兼容模式）| openai-compat | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 智谱 GLM | openai-compat | `https://open.bigmodel.cn/api/paas/v4` | `glm-4` |
| OpenAI | openai-compat | `https://api.openai.com/v1` | `gpt-4o-mini` |
| Ollama（本地）| ollama | `http://localhost:11434/v1` | `qwen2.5` |

- pi 侧（**已实现**，见 `app/src/agent-subprocess/model-resolve.ts`）：所有 OpenAI 兼容端点统一构造 `openai-completions` 的 `Model` 字面量（自带 `baseUrl`），**无需 `registerApiProvider`**；`new Agent({ initialState:{model,tools}, getApiKey })`；key 经 env 注入子进程。
- 首启检测到 `http://localhost:11434` 可达 → 直接走 Ollama 模板（零 key）；否则引导填 `openai-compat` key（默认推荐 DeepSeek 模板 + 注册链接）。

## 9 · 安全策略（具体）

| 项 | M0 规则 |
|---|---|
| **默认工作区根** | 首启向导选一个文件夹；默认 `~/Fleet/workspace`（不存在则创建）。记入 config |
| **路径校验** | 所有 `fs.*` / `shell.run cwd` 用 `path.resolve(root, p)` 后必须 `startsWith(root)`；拒绝 `..` 越界与指向 root 外的 symlink |
| **shell 允许/禁止** | **默认拒绝危险模式**（denylist）：`rm -rf /`、`sudo`、`shutdown/reboot`、`mkfs`、fork bomb `:(){`、`curl/wget ... | sh`、`> /dev/`、改全局环境等；命中直接拒绝（连审批都不弹） |
| **哪些必须审批** | M0：**所有 `shell.run` 必审批**；`fs.list`/`fs.read` 为 `safe` 不审批（但仍受路径校验） |
| **执行方式** | `shell.run` 经审批后用 `spawn("bash", ["-lc", command])`（Win 用 `powershell -Command`），不拼接用户串到内层；超时 60s、输出上限 64KB、cancel→`tree-kill` |
| **API key 存储** | Electron `safeStorage`（系统钥匙串加密）→ 密文存 electron-store，记 `apiKeyRef`；**绝不**回传 renderer（只给掩码 `sk-***`）、**绝不**进 JSONL/日志；子进程经 env 拿明文 |
| **工具调用日志** | 默认**落盘** `.fleet/logs/tools-YYYYMMDD.jsonl`：工具名/参数（密钥脱敏）/审批决定/耗时/结果摘要；设置页可关 |
| **用户拒绝后** | agent 收到的 `tool.result` = `{ok:false, error:{code:"rejected_by_user", message:"用户拒绝了该操作"}}`，作为该工具的观察值；**run 不中断**，模型据此改策略（道歉/换方案/询问）。用户若要停整个 run 用「取消」 |

## 10 · UI 验收标准（首屏六件套）

| 区域 | 必须有 | 验收（能做到 X） |
|---|---|---|
| **首启向导** Onboarding | 选工作区 → 选模型（检测到 Ollama 给一键；否则填 key + DeepSeek/Qwen 模板按钮）→ 完成 | 走完向导即写入 config + 建工作区，进入主界面 |
| **聊天区** Chat | 输入框、发送、流式助手气泡、消息列表、内联工具卡片（请求/审批/结果）| 发一句→看到流式回复；触发 `shell.run`→看到工具卡片与状态流转 |
| **左侧 Agent 状态** AgentSidebar | 内置 Agent 一条，实时态：空闲/思考/待审批/执行工具/失败 | 跑任务时状态随 EventStream 实时变 |

| **失败态** FailureBanner | 模型/网络/工具错误清晰展示 + 重试；取消显示为「已取消」 | 断网/错 key 时有明确失败态与重试，不白屏 |
