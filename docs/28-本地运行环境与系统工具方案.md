# 28 · 本地运行环境与系统工具方案

> 状态日期：2026-06-20
> 定位：把本机 CLI、运行时、sidecar、浏览器 helper、项目环境和 Agent 可用能力做成一个可观测、可诊断、可授权的系统工具层。它服务两类人：开发者能少折腾环境，Agent 能知道当前机器能做什么、该用哪个工具、哪里会冲突。
> 边界：LobeHub 只能黑盒参考产品边界和行为，不复制源码、类型、组件、文案或目录结构。Fleet 实现必须落回 craft main process、RPC、permission、session timeline 和本地数据边界。

---

## 1 · 为什么这是关键底座

Fleet 后续要做 CLI Runtime、ProjectPack、MarkItDown、codegraph、rtk、浏览器自动化、Figma/Stitch bridge、字体扫描、动画/视频导出。它们都依赖本机环境。

如果没有统一的系统工具层，会出现：

- 用户不知道缺的是 `node`、`python`、`bun`、`uv`、`rg` 还是某个 CLI agent。
- Agent 以为工具可用，实际运行时 PATH 不同导致失败。
- Electron 从 Finder 启动时 PATH 比终端短，`which codex` 找不到，但终端里能跑。
- 同一个工具有多个版本，项目要求和全局版本冲突。
- 每个功能各自探测环境，错误提示不一致，权限和 timeline 也断开。

所以它不是普通设置页，而是**本机能力注册表 + 健康诊断 + Agent 可用能力目录**。

## 2 · LobeHub 做法复盘（只学行为）

本地复查 LobeHub 后，系统工具页实际分成三块：

1. **Tool Detector**
   - 分类展示工具：运行环境、CLI Agents、内容搜索、文件搜索、浏览器自动化。
   - 每个工具固定显示，即使未检测到也占位，避免用户不知道这个能力存在。
   - 展示版本、路径、可用/不可用、重新检测、复制路径。
2. **App Environment**
   - 展示 Electron、Chromium、内置 Node.js 版本。
   - 区分“App 自带运行时”和“用户系统里的命令行工具”。
3. **CLI Test（开发模式）**
   - 允许在设置页直接跑少量诊断命令，输出 stdout/stderr/exit code。

主进程侧是一个 detector manager：

- detector 按 category 注册，有 name、description、priority、detect()。
- 结果缓存；可 force redetect。
- IPC 暴露 detectTool / detectAllTools / detectCategory / getBestTool / clearCache。
- 检测不仅看 `which/where`，还会验证 `--version` 或 `--help` 输出关键字，避免撞名。
- macOS/Linux 会补 login shell PATH，解决桌面 App 启动环境和终端环境不一致。
- Windows 会处理 `.exe/.cmd/.bat`，避免误选不可执行 shim。
- 某些 CLI agent 有 well-known path fallback，例如 App bundle 内置 CLI 不在 PATH 里也能发现。

Fleet 要吸收这些产品和工程边界，但不能复制实现。

## 3 · Fleet 的目标形态

Fleet 的系统工具层分两级：

| 层 | 作用 | 例子 |
|---|---|---|
| **全局系统工具** | 这台机器有哪些可用能力 | node、python、bun、pnpm、uv、git、rg、fd、browser helper、Gemini/Codex/Grok/Hermes/OpenCode CLI、ProjectPack sidecar、MarkItDown sidecar、codegraph、rtk |
| **项目运行环境** | 当前项目应该用哪些工具、版本和工作目录 | 该项目用 pnpm 还是 bun、Python venv/uv、Node 版本、包管理器 lockfile、测试命令、构建命令、环境变量文件、容器/远端 workspace |

界面上应该有两个入口：

- **设置 → 系统工具**：看全局能力，修本机环境。
- **项目 → 环境**：看当前项目的实际运行环境和冲突。

Agent 使用时不应该自己乱猜 PATH。它应该先读 Fleet 的能力目录，知道“可用工具、推荐工具、禁用工具、需要用户授权的工具、当前项目 override”。

## 4 · Tool Capability 契约

每个工具统一记录：

| 字段 | 说明 |
|---|---|
| `toolId` | 稳定 ID，例如 `node`、`python`、`gemini-cli`、`project-pack` |
| `category` | `runtime` / `package-manager` / `cli-agent` / `search` / `browser` / `context` / `design` / `video` / `custom` |
| `displayName` | UI 名称 |
| `status` | `available` / `missing` / `broken` / `conflict` / `disabled` / `unknown` |
| `version` | 检测到的版本；没有就为空 |
| `path` | 最终执行路径 |
| `resolvedPathEnv` | 如果靠 login shell PATH 找到，记录当时 PATH，后续 spawn 必须带上 |
| `source` | `bundled` / `system-path` / `login-shell-path` / `project-local` / `well-known-path` / `custom` |
| `scope` | `global` / `project` / `workspace` / `runtime` |
| `priority` | 同类工具优先级 |
| `capabilities` | 能做什么：`run-js`、`run-python`、`package-install`、`acp-stdio`、`repo-pack`、`doc-convert`、`graph-query`、`browser-control` |
| `risk` | `read-only` / `local-exec` / `network` / `file-write` / `external-upload` |
| `lastCheckedAt` | 最后检测时间 |
| `diagnostics` | 失败原因、stderr tail、修复建议 |
| `userOverride` | 用户手动指定 path/args/env 时记录 |

重点：**检测到工具不等于允许 Agent 使用工具**。使用仍要走 craft permission、session timeline 和风险分级。

## 5 · 检测分类

第一版分类：

### 5.1 App 内置环境

- Electron
- Chromium
- App bundled Node / Bun（如果存在）
- Fleet 版本、craft base commit、当前 build channel

用途：排查“App 自己能不能运行”。

### 5.2 基础运行时

- node / npm / pnpm / bun / bunx
- python / uv / pip
- git
- shell（zsh/bash/powershell/cmd）

用途：项目构建、脚本、sidecar、工具安装。

### 5.3 CLI Agent / ACP Runtime

- grok
- hermes
- opencode
- gemini
- qwen
- codex
- claude
- custom ACP runtime

检测要求：

- 不只看命令存在，还要跑 `--version` 或 `--help` 验证身份。
- 能力要拆开：`cli-exists`、`acp-entry-confirmed`、`auth-likely-ready`、`health-test-passed`。
- “检测到 CLI”不代表 production mapping 可用，unsupported 仍要明确提示。

### 5.4 搜索与代码理解

- rg / grep / ag
- fd / find / mdfind
- codegraph indexer

用途：Agent 读项目、上下文压缩、代码定位。

### 5.5 上下文效率 sidecar

- ProjectPack / repomix-like adapter
- MarkItDown-like converter
- rtk reducer
- codegraph
- Headroom sidecar（未绿灯前仅 optional）

用途：打包、转换、压缩、审查。

### 5.6 浏览器与设计工具

- BrowserPane / CDP helper
- Playwright/Chrome path（如后续需要）
- Figma bridge
- 字体扫描服务
- 图片/视频处理工具
- motion/video renderer

用途：浏览器标注、Artifact Studio、Figma/Stitch、动画导出。

## 6 · 冲突诊断

Fleet 不能只显示“可用/不可用”，还要诊断冲突：

| 冲突 | 检测方式 | UI 提示 |
|---|---|---|
| App PATH 与终端 PATH 不一致 | 比较 `process.env.PATH` 和 login shell PATH | “终端可用但 App 不可用，已从登录 shell PATH 找到，运行时将携带该 PATH” |
| 多版本冲突 | `which -a` / `where` 多路径 + version | “发现多个 node/python，当前使用 X，项目可能要求 Y” |
| 项目 lockfile 冲突 | 检查 `bun.lock`、`pnpm-lock.yaml`、`package-lock.json`、`yarn.lock` | 推荐对应包管理器，不自动混用 |
| Python 环境冲突 | 检查 `.venv`、`pyproject.toml`、`uv.lock`、`requirements.txt` | 优先项目 venv/uv，不直接用系统 python |
| CLI shim 依赖缺失 | 验证 shim 启动时是否能找到 node/python | “命令路径存在，但运行失败：env node not found” |
| 权限缺失 | 检查文件权限、macOS quarantine、可执行位 | 给修复建议，不自动 chmod |
| 网络/代理影响 | 只做诊断，不偷读凭据 | 标明代理状态未知/需用户确认 |

冲突诊断要给 Agent 可读的结构化结果，避免 Agent 反复试错浪费 token。

## 7 · 项目环境 Profile

每个项目有一份 `ProjectEnvironmentProfile`，不写进第三方项目源码，默认存 Fleet 本地状态：

- 项目根目录、git root、workspace id。
- 推荐 package manager。
- 推荐 node/python/bun/pnpm/uv。
- build/test/typecheck/lint 命令。
- env file 候选：只记录路径和 hash，不读取 secret 内容。
- sidecar 可用性。
- 远端 workspace / local-only 能力差异。
- 最近一次环境检测结果和修复建议。

Agent 开始任务前读取它：

1. 先知道当前项目该用什么命令。
2. 运行命令前如果环境缺失，先提示修复，不盲跑。
3. 如果用户换了工具版本，重新检测并更新 profile。

## 8 · Agent 使用规则

系统工具层对 Agent 暴露三类接口：

| 接口 | 作用 | 权限 |
|---|---|---|
| `env.listTools` | 读能力目录 | 只读，可自动 |
| `env.diagnoseProject` | 诊断当前项目环境 | 只读，可自动 |
| `env.runRepair` | 执行修复命令，如安装依赖、切换解释器、生成配置 | 写入/执行，必须权限卡 |

Agent 不能直接用“我猜机器有 node”作为依据。需要运行命令时：

- 先查 `env.listTools` 或项目 profile。
- 如果工具 missing/broken/conflict，先解释原因和修复建议。
- 真正执行修复、安装、写配置时走 permission。
- 所有诊断和修复写入 session timeline。

## 9 · UI 设计

系统工具页不做复杂仪表盘，第一版就是清晰列表：

- 左侧分类：运行时、包管理器、CLI Agent、搜索、上下文、浏览器、设计/媒体、项目环境。
- 每行：名称、版本、状态、路径、来源、风险、最后检测时间、复制路径、重新检测。
- 状态颜色：
  - 绿色：可用。
  - 黄色：可用但有冲突/非推荐版本。
  - 红色：不可用或验证失败。
  - 灰色：未检测 / 当前平台不适用。
- 详情抽屉：检测命令、stderr tail、PATH 来源、修复建议、依赖它的 Fleet 功能。
- 项目环境页：显示当前项目推荐命令、缺失项、冲突项、Agent 可用能力。

不要做“自动安装所有依赖”按钮。第一版只做诊断和明确修复建议；安装/改配置必须用户确认。

## 10 · 实现顺序

### ENV-1 全局 Tool Registry

- 在 main process 建 detector registry。
- 支持 category、priority、cache、force redetect。
- 最小工具：node、npm、pnpm、bun、python、uv、git、rg、fd、grok、hermes、opencode、gemini、codex、claude。
- 输出统一 `ToolCapability`。

### ENV-2 PATH 与多版本诊断

- 支持 login shell PATH fallback。
- 支持 `which -a` / `where` 多路径。
- 支持 `resolvedPathEnv` 传给后续 spawn。
- 支持 macOS app bundle well-known path。

### ENV-3 System Tools UI

- 设置页新增系统工具列表。
- 展示版本、路径、来源、状态、修复建议。
- 支持重新检测、复制路径、查看详情。

### ENV-4 Project Environment Profile

- 进入项目时自动只读扫描 lockfile、venv、package scripts、git root。
- 给出推荐命令和冲突提示。
- Agent 启动任务前可读取。

### ENV-5 Agent API 与权限

- `env.listTools` / `env.diagnoseProject` 只读。
- `env.runRepair` 走 permission + timeline。
- CLI Runtime、ProjectPack、Design/Video sidecar 全部依赖这里的 capability。

### ENV-6 与 Usage/Context Report 打通

- 环境导致失败时，在报告里归因。
- 记录“因为缺失工具导致外部审查/打包/导出不可用”。
- 记录工具版本变化对任务结果的影响。

## 11 · 不做什么

- 不自动安装全局工具。
- 不自动改用户 shell 配置。
- 不自动 chmod、改 PATH、改系统 Python。
- 不读取 `.env` secret 内容。
- 不把检测到的外部 CLI 当作已授权可执行。
- 不因为某工具缺失而让 Agent 自行下载未知二进制。
- 不引入第二套执行通道；所有执行仍走 craft permission / timeline。
