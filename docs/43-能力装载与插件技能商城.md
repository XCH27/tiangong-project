## 0 · 用户洞察（同步留档，本方案的出发点）

> 现在 Codex、Claude、Cursor 等都只能**人类手动**选择、下载插件/Skill。下载一堆之后，开发不同项目又要手动管理这些东西。**Skill 和工具越来越多，Agent 的注意力有限——这些东西的"管理"才是真正的大问题。**
>
> 我要的是：**不同工作区里，让 Agent 自己选择给自己、给队员加载哪些工具/Skill 组合、开放哪些权限**，这样才能真正实现完美的并行开发。但我现在又有 CLI、API、MCP 等多种入口，在这种情况下要**怎么避免冲突、实现多项目插件/工具的隔离**。

把它翻译成一句产品判断：**别人是"人装一堆，全程常驻，跨项目互相打架"；Fleet 是"全装进目录，按工作区/身份/任务由 Agent 装载最小集，按 scope 隔离运行"。** 装载（什么时候挂给谁）与安装（本机有什么）彻底分离，才解决"注意力被工具表撑爆 + 多项目串味"。

## 1 · 三平面模型（安装 ≠ 装载 ≠ 运行）

| 平面 | 回答 | 单一真相 | 类比 |
|---|---|---|---|
| **能力目录（Catalog）** | 本机/本工作区**有哪些**能力可用 | `CapabilityCatalogService` | 应用商店里已下载的 App |
| **能力装载（Loadout）** | 此刻**给谁、在哪个范围挂载**哪些能力、开多大权限 | `CapabilityLoadoutService` | 手机主屏上摆出来的那几个 App |
| **能力运行（Runtime/Isolation）** | 挂载的 CLI/API/MCP 进程**怎么不打架** | `CapabilityResolver` + 资源租约 | 每个 App 各自的沙箱/账号 |

别人把这三件事混成一件（装=开=常驻全局）。Fleet 拆开：**目录全量、装载最小、运行隔离。**

## 2 · 能力目录：统一描述符（什么存在）

所有能力（不论来源）抽象成同一个描述符，Agent 用一个工具就能枚举整张目录。

```ts
export type CapabilityKind =
  | 'internal-action'   // Registry 里的内部动作（docs/40），Fleet 自有，最高优先
  | 'skill'             // Skill 包（docs/39）
  | 'mcp'               // MCP server / 其工具集
  | 'cli-runtime'       // 本机 CLI（Goose/Claude Code/Codex，via ACP）
  | 'api-provider'      // 模型 API 连接
  | 'connector'         // 外部应用连接器（GitHub/Drive…）
  | 'plugin'            // 上述若干项的打包集合（bundle）

export interface CapabilityDescriptor {
  id: string                       // 全局唯一稳定 id，命名 `kind:source/name`，如 `mcp:figma/figma`
  kind: CapabilityKind
  title: string; description: string            // 默认中文（见 §8 汉化）；第三方原文经 i18n 包裹
  source: 'integrate' | 'adapt'    // D24：集成（vendor 绿灯源码）/ 兼容（adapter/BYO/sidecar）
  licenseGate: 'green' | 'pending' | 'blackbox' | 'proprietary'  // D20 许可证闸
  version: string; checksum?: string            // 版本钉住（D24 健康检测）
  health: 'ready' | 'degraded' | 'missing' | 'unverified'
  locality: 'LOCAL_ONLY' | 'REMOTE_ELIGIBLE'    // 规则 14
  permissionCeiling: 'L0' | 'L1' | 'L2' | 'L3'  // 该能力可达的最高权限；装载不得越过
  cost?: { kind: 'token' | 'subscription' | 'api' | 'external' | 'free'; note?: string } // 规则 21 诚实成本
  domainTags: string[]             // 身份匹配用：'code'|'design'|'video'|'review'|'context'|'browser'…
  provides: { surfaces?: string[]; actionIds?: string[]; tools?: string[] } // 对外暴露什么
  dependsOn?: string[]             // 依赖的其它能力 id
  conflictsWith?: string[]         // 互斥能力 id（§5）
  singletonScope?: 'global' | 'workspace' | 'session'  // 同一 scope 内是否只能一个实例（§5）
  resourceNeeds?: Array<'port' | 'home-dir' | 'credential' | 'pty' | 'browser'> // 需隔离的运行资源
}
```

- **internal-action 不在商城卖**：它们是 Fleet 自有、随版本走，自动进目录；商城卖的是 skill/mcp/cli/api/connector/plugin。
- **目录写操作**（install/enable/disable/update）本身登记成 `settings`/`plugin` 面的 internal actions，走 permission + timeline。

## 3 · 能力装载：分层 scope（挂给谁、在哪）

装载在四层 scope 上叠加解析，**后者覆盖前者**；解析结果就是某个 actor 在某个上下文里真正能看到的能力集 + 权限画像。

| scope | 谁定义 | 作用 |
|---|---|---|
| **全局默认** | 用户 / 管理 Agent | 所有工作区的兜底（如核心 internal actions + 记忆工具） |
| **工作区默认** | 管理 Agent（用户可改） | 该项目类型常驻的能力组合（代码项目挂 codegraph+git；设计项目挂 canvas+browser） |
| **身份/角色** | 管理 Agent / 队长 | 按 identity label 裁剪（剪辑队员只挂剪辑域，见 `docs/17 §3.2`） |
| **会话/任务** | 队长（派发时） | 单任务临时增减（这次要查 GitHub → 临时挂 connector，任务结束回收） |

```ts
export interface CapabilityLoadout {
  scope: { level: 'global' | 'workspace' | 'identity' | 'session'; refId?: string }
  enabled: Array<{
    capabilityId: string
    permissionProfile: 'L0' | 'L1' | 'L2' | 'L3'  // ≤ 该能力 permissionCeiling
    resourceBinding?: { profileDir?: string; port?: number; credentialRef?: string } // §5 隔离
  }>
  authoredBy: { actor: 'user' | 'manager' | 'leader'; agentId?: string }
  basis?: string                  // Agent 装载时的依据（记忆/偏好/规则/best-combo），写 timeline
}
```

**装载即裁剪**：构建某 session 的工具表与上下文时，按解析后的 loadout 过滤 `InternalActionRegistry` + 注入对应 MCP/CLI/Skill。这是 `docs/17 §3.2`「只挂 3-4 个匹配工具」的全量实现：工具表恒为该 actor 的最小集，不是整张目录。

## 4 · 谁来选：Agent 自主装载（与别人最大的差异）

别人只有「人类手动选」。Fleet 有**逃生舱 + Agent 自主**两条，且 Agent 自主是默认主线。

### 4.1 三种作者
- **用户（逃生舱，D1）**：在设置里 pin / 排除 / 锁定某能力，作为硬约束覆盖 Agent 选择。
- **管理 Agent**：拥有**工作区默认装载** + 派发任务时为队员**组装身份/任务装载**。它是装载的所有者（与它拥有记忆、状态一致，`docs/17 §2`）。
- **队长 Agent**：在项目内为队员组装**任务级**装载（项目内最知道谁该用什么）。

### 4.2 选择依据（让装载越来越聪明）
Agent 组装装载不是拍脑袋，而是综合：
1. **任务描述 × `domainTags`**：任务语义匹配能力领域标签。
2. **identity label**：身份决定基线域（剪辑/代码/审查…）。
3. **记忆 ↔ Skill 飞轮**（`docs/05 §4.1`）：召回"这类任务历史上用过哪些能力/Skill 成功"，优先装载。
4. **最佳组合目录**（D24/`docs/29 §1.5`）：每类能力 Fleet 预配最优组合，Agent 直接取，不用满世界找。

### 4.3 装载是一次 internal action（可审计、可撤销）
组装/应用装载本身登记为内部动作，人和 Agent 同一 id：

| id | verb | 权限 | 说明 |
|---|---|---|---|
| `capability.list` | read | L0 | 枚举目录（Agent 发现能力） |
| `capability.resolve_loadout` | read | L0 | 解析某 scope/actor 的有效装载 |
| `manager.compose_loadout` | mutate | **L2** | 管理 Agent 设工作区/身份默认装载 |
| `team.assign_loadout` | mutate | **L2** | 队长为队员设任务装载 |
| `plugin.install` / `plugin.enable` | mutate | **L2/L3** | 装入目录 / 启用（外发/付费类 L3） |

- 装载里**新增 L2/L3 能力或抬高 permissionProfile** → 走 permission 确认（不能由"开了自动决策"代答 L3，规则 26）。
- 每次装载变更发 `loadout_changed` SessionEvent，带 `authoredBy/basis`，undo = 恢复上一份装载快照。
- Agent 暴露方式沿用 `docs/40 §7`：不为每个能力建工具，用 `list_capabilities` + `propose_loadout(invocation)` 两个通用工具，工具表恒常数级。

## 5 · 多项目隔离与冲突避免（CLI/API/MCP 不打架）

用户的硬问题：同时有 CLI、API、MCP，多项目并行怎么不串味。三道隔离：

### 5.1 工作区能力命名空间
每个工作区一套**独立**的：启用能力集 + 配置/凭据目录（`<workspace>/.fleet/`）。API Key、MCP server 配置、CLI runtime profile **绑定到 workspace（或 session）scope，不写全局可变单例**。A 项目改 MCP 配置不影响 B 项目。

### 5.2 每会话运行实例 + 注入环境
CLI runtime 进程、MCP server 按 session（或 workspace）**各起一份**，注入独立 `HOME/env/cwd`（复用 D4 凭据路径隔离）。两个项目的 Claude Code / 同名 MCP 各跑各的，互不覆盖登录态与缓存。

### 5.3 冲突解析器 + 资源租约
描述符声明 `conflictsWith` / `singletonScope` / `resourceNeeds`，`CapabilityResolver` 在装载应用前判定：

| 冲突类型 | 解析策略 |
|---|---|
| 同 `singletonScope` 互斥（如两个抢同端口的 MCP） | 拒绝并提示，或分配不同端口 / 串行化（资源租约排队） |
| CLI/API 凭据冲突 | 每 scope 独立 `profileDir`，**绝不共享写全局配置** |
| 工具 id 跨插件撞名 | 强制命名空间 `pluginId:tool`，不互相遮蔽 |
| 本机端口/PTY/浏览器实例 | 资源租约（类比 `docs/42 §1.2D` 面板租约）：登记 owner + 超时释放 |

- 本机类能力（cli/pty/mcp-local/browser）`locality='LOCAL_ONLY'`（规则 14）。
- 这套**不需要物理沙箱/Daemon**（那是 `docs/42` M3 条件项）；单进程内靠 scope 命名空间 + 注入环境 + 租约即可隔离。

## 6 · 插件 / Skill 商城（UI 形态与汉化）

参考 Codex/Cursor/Claude 的商城形态（用户提供截图），但把"安装"接到三平面模型上：**商城只负责把能力装进目录，"挂给谁"由装载系统决定。**

### 6.1 UI 挂点（复用现有壳，不新建框架）
- 落 **设置页**：`settings-pages.ts` 注册新页 `capabilityMarketplace`，复用现有设置壳（参考 `GitHubSettingsPage`/`LabelsSettingsPage` 模式），**不新建 WorkbenchShell**（`docs/42` 禁令 #4）。
- 顶部页签：`插件` / `技能` / `连接器(MCP)` / `能力装载`。
- 来源筛选：`由 Fleet 提供`（best-combo 精选）/ `社区` / `个人`。
- 区块：`已安装`（目录）+ `推荐`（best-combo）+ 搜索。
- 每条卡片：图标、标题、描述、来源徽标（集成/兼容）、许可证闸状态、健康态、`安装`/`已安装`/`启用`、`…` 详情。
- **能力装载页**：按工作区/身份展示当前有效装载，可查看 Agent 装载的依据（basis），用户可 pin/排除/锁定。

### 6.2 汉化（规则 35/36，合并自原 `docs/08`）

**核心原则：翻译只在显示层，执行 / 存储 / 匹配永远用原文。** 改原文就会破坏执行，也违反"不另起第二套真相"。

- **Fleet chrome 默认中文**：截图里 `Featured`/`Try in chat`/`Add`/`Manage`/`Discover`/`Infrastructure` 等一律汉化为 `推荐`/`在对话中试用`/`安装`/`管理`/`发现`/`基础设施`。i18n key 由 **Lead 在 Wave 0 冻结**后加入 `i18n/locales/*.json`（规则 36，并行 Agent 不自行改）。
- **第三方文本本地化（旁路缓存层）**：插件 `name/description/README`、CLI `--help`/命令说明、Skill frontmatter `description` 等英文文本 → 算 hash → 查本地译文缓存 → 命中显示中文，未命中后台翻译（本地/云模型）后入缓存。**UI 显示译文；命令照原样跑、Skill 照原样注入、插件照原样安装。** 每条译文带"显示原文"开关，用户可纠正（用户译文优先回写缓存）。对 craft 是只读旁路，不动 Skill 文件/CLI/插件包。
- **已交付引擎**：`app/packages/shared/src/localization/localization-service.ts`——零依赖同构（浏览器+node）：`peek`(同步取策展/缓存)、`localize`(策展 > 缓存 > 翻译并缓存)、`correct`(用户纠正)；人工策展优先、`clampShort` 压短、FNV hash 当缓存键；已在 Node 22 实跑 11 项断言全过。商城/CLI/Skill 说明统一调 `LocalizationService.localize(text, 'plugin'|'cli'|'skill')`。

### 6.3 插件市场自动同步（合并自原 `docs/08`）
- **不自创格式**：建在 MCP server(+registry) + Skills + Claude Code plugin/marketplace（git 托管清单）标准上。
- **自动同步**：定期拉清单 diff → 列出"有更新的插件" → 一键 / 可设自动更新。同步的是"有哪些插件、什么版本"；更新与否可自动或手动。
- 安装/更新仍走 D20 许可证闸 + D24 集成/兼容分流；插件包零改动。

## 8 · 落地路线（挂 `docs/01` / `docs/42` 主干，不抢主线）

建在 M0 Internal Action Registry 之上，分阶段：

| 阶段 | 目标 |
|---|---|
| **CAP-0（M0/M1）** | `CapabilityDescriptor` 契约 + 目录服务最小版：把已有 internal-action/skill/mcp/cli/api 盘点进目录；Plugin Registry 许可证闸（`docs/01` M0 #7）可标状态、可拒 proprietary |
| **CAP-1（M1）** | 装载解析 + 工作区命名空间 + 身份裁剪全量（扩展 `docs/17 §3.2`）：工作区/身份级 loadout 能真正过滤工具表与上下文 |
| **CAP-2（M1/M2）** | 多项目隔离 v1：CLI/MCP 每会话独立 profileDir + 注入 env + 冲突解析器 + 资源租约 |
| **CAP-3（M2）** | Agent 自主装载：`manager.compose_loadout` / `team.assign_loadout`，依据接记忆飞轮（`docs/05 §4.1`）+ best-combo（D24）；装载变更 permission + timeline + undo |
| **CAP-4（M2）** | 商城 UI + 汉化：插件/技能/连接器/装载 四页签，Fleet/社区/个人 来源；安装走 D20 闸 + D24 分流 |
| **CAP-5（M3）** | 社区商城分发、跨工作区装载模板共享、（如出现真实需求）Daemon/沙箱级隔离 |

## 9 · 验收（usable 硬标准）

- [ ] 同一能力目录里能枚举 internal-action/skill/mcp/cli/api/plugin，带来源（集成/兼容）、许可证闸、健康态。
- [ ] 一个工作区装载代码组合、另一个装载设计组合；切换工作区后，Agent 工具表随之变化，不串味。
- [ ] 拉起 `video_editor` 队员，其工具表只含剪辑域 3-4 项，看不到 `terminal.run_command` 与代码工具。
- [ ] 管理 Agent/队长能 `propose_loadout` 给队员增减能力；新增 L2/L3 能力弹权限；变更进 timeline 可撤销，带 basis。
- [ ] 两个项目各自的 Claude Code / 同名 MCP 并行运行，凭据/缓存/端口互不覆盖（独立 profileDir + 注入 env）。
- [ ] 冲突能力（抢同端口的两个 MCP）被解析器拒绝或分配/排队，不静默崩。
- [ ] 商城全中文 chrome；安装 proprietary 插件被许可证闸拒绝（D20）；安装迭代型项目走兼容/sidecar（D24）。
- [ ] 关掉装载系统，行为回退到"全量工具表 + 全局配置"的 craft 原样（接口隔离可验证）。

## 10 · 反模式

- 把"安装"等于"全程常驻全局"（应安装进目录、按 loadout 装载，§1）。
- 给每个能力各做一个 Agent 工具（应 `list_capabilities` + `propose_loadout`，§4.3）。
- CLI/API/MCP 写全局可变单例配置（应 workspace/session scope + 注入 env，§5）。
- 新建商城用第二套壳/导航（应复用设置页，§6.1）。
- 商城 chrome 留英文（应汉化，key 由 Lead 冻结，§6.2）。
- 让 Agent 靠截图/DOM 操控商城或装载（应走 internal action，规则 19a）。
