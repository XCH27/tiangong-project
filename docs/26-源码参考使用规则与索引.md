硬规则：

- MIT/Apache-2.0 只是进入候选池，不自动等于绿灯；用户明确核准后，必须写入上方绿灯表并标明 commit、复制范围、归因方式。

- 未核准前，即使 LICENSE 看起来宽松，也只能参考产品行为、公开文档、交互目标和能力清单。
- 黑盒参考项目禁止复制源码、测试、配置、类型定义、样式、资源文件、文案和结构性实现。
- `golutra` 本地许可证为 BSL 1.1，按高风险黑盒处理。

## 1.2 · 2026-06-19 新增候选与专项来源边界

### 1.2.1 · 最新开源 Agent / CLI 候选更新

官方来源核对见 `docs/12-最新开源Agent与CLI参考更新.md`。结论：

- Gemini CLI、Qwen Code、Cline、Roo Code 均显示为 Apache-2.0 开源项目，但尚未由用户写入绿灯表，不能复制源码。
- Gemini CLI 不再作为 Fleet 内置 runtime 探测路线；Google CLI 主线改为 Antigravity（命令 `agy`）。如后续重新评估 Gemini，只能作为 opt-in 参考，不得自动恢复内置 mapping。
- Qwen Code 已进入 ACP 生态，但公开 README 中最明确的是 `qwen serve` daemon / HTTP+SSE 方向；Fleet 当前 stdio ACP client 不能直接假设可用。
- OpenHands / Agent Canvas 适合学习 local/remote/cloud backend 和 sandbox 边界，不作为单个 stdio runtime 直接接入。
- Continue 虽是 Apache-2.0，但官方 repo 已标记 read-only / no longer actively maintained，只作为历史参考。

## 3 · 复用要求

每个功能模块动工前必须写清：

1. craft 中已有的路径和能力。
2. AionUi 是否有可直接迁移的绿灯实现。
3. 是否需要参考其它项目；若项目已在绿灯表，可写清可复制范围，否则只能写参考点。
4. 需要保留的许可证、SPDX、NOTICE 或子目录独立 LICENSE。
5. 验收命令和用户可见路径。

每次从绿灯项目迁移源码，还必须更新来源清单：

| 字段 | 要求 |
|---|---|
| Fleet 模块 | 新代码服务哪个 Fleet 功能 |
| 来源项目 | 必须是绿灯表中的项目 |
| 来源路径 | 原始文件/目录路径 |
| 来源版本 | commit/tag/date |
| 迁移方式 | 原样复制、局部复制、改写、模式迁移 |
| 许可证处理 | 是否保留文件头、SPDX、NOTICE/归因 |
| 修改说明 | Fleet 做了哪些改动 |

建议记录到 `docs/27-源码归因清单.md`。

## 4 · 绿灯源码迁移归因规则

- 复制整文件时保留原文件头、版权声明和 SPDX。
- 改写或拆分绿灯项目文件时，在新文件头或邻近注释标明 `Portions derived from <project>`，并附原路径、许可证、迁移日期。
- 在产品第三方声明或 NOTICE addendum 中加入必要归因；若来源项目有 NOTICE 文件，必须合并保留。
- 不默认复制 logo、品牌名、截图、gif、图标等商标/品牌资产，除非用户单独确认。
- 对 open-design 的 templates/design-systems/skills/plugins 子目录，复制前必须检查该子目录是否另带 LICENSE 或第三方归因。
- 迁移任务说明中必须列明来源项目、文件路径、迁移方式和验证命令。

## 5 · 禁止事项

- 禁止另起一套自研 Electron/Vite/IPC/renderer 架构。
- 禁止从 Kun、Cherry、Zed、LobeHub、Warp、OpenCode、cmux、golutra、multica、hermes-agent、cc-switch、AstrBot、context-mode、cockpit-tools、headroom、repomix、markitdown、OpenHands、OpenClaw、browser-harness、CloakBrowser 等红灯/黄灯/未核准项目复制源码。
- 可以基于产品需求自研 UI，但不得复制未核准项目的源码、结构性实现、品牌资产、截图切图或高度近似布局。
- 禁止把 Git、浏览器、Skill、MCP 都塞进设置页；这些必须成为工作台能力。
- 禁止把账号额度、凭证读取、自动切号、私有 usage 接口抓取混进 CLI Runtime 探测。
