# Fleet 项目白皮书 · 愿景 / 痛点 / 理念（WHY 的单一真相 · 北极星）

> 状态日期：2026-06-26
> 定位：这是项目的 **WHY 单一真相**——记录"做这个项目是为了什么、要解决谁的什么痛点、背后的思想理念"。它是北极星，不是路线表。
> 分工：**WHY 看本文** → **WHAT（产品形态）看 `docs/01`/`docs/02`/`docs/18`** → **HOW（路线/架构）看 `docs/42`** → **决策看 `docs/04`** → **状态看 `docs/32`**。
> 给所有 Agent：**优化项目前先读本文对齐意图，再判断"现在的方案是不是最优、有没有更好的方法"，然后才动手——不要盲目执行（见 §5 评审协议）。** 用户不必每换一个 Agent 就重讲一遍想法；想法沉淀在这里。

---

## 0 · 怎么用这份白皮书

1. **先对齐 WHY**：任何改动先回到对应理念（§3），确认没违背初衷。
2. **再判断最优**：用 §5 评审协议问"这是不是最优解、有没有更好的方法"。发现更好的方法，**先改本文理念 / 或 `docs/04` 决策，再改下游实现**——不闷头改代码。
3. **按追溯表找落地**（§4）：每条理念都指向"具体落地是哪个文档"。
4. **每条理念可被推翻**：附"可被推翻的条件"。世界变了、有更优解了，就在这里改，而不是让理念和实现各走各的。

## 1 · 一句话愿景

**Fleet = 人类主导、AI 辅助的本地「AI 工作创作台」。** 人和 AI 在同一个项目里完成开发、设计、文档、AIGC、素材、视频、审查、交付——用同一套工作台、session、权限、记忆、时间线和成本账本，而不是把一堆聊天工具和外部软件拼在一起。

> Fleet 不做"多 CLI Agent 管理器"。CLI / ACP / MCP / API 只是入口和外部桥；真正的差异化是让 Agent **低 token、高安全、可回放**地操控 Fleet 内部结构化对象，并且**自己管理用什么能力**。

## 2 · 我们要解决的痛点（用户洞察留档）

| # | 痛点（现状） | 谁痛 |
|---|---|---|
| 痛点 1 | 工具各自为政：多个聊天工具/外部软件简单拼接，状态分裂、来回搬运 | 所有用户 |
| 痛点 2 | **能力管理才是大问题**：Skill/工具/插件越来越多，Agent 注意力有限；别人(Codex/Claude/Cursor)只能人类手动选，下载一堆后跨项目又要重新管理、互相打架 | 重度用户 / 多项目用户 |
| 痛点 3 | 大项目单 Agent 上下文被微观操作和报错日志撑爆、推进慢；但乱开团队又过度工程化 | 长程开发 |
| 痛点 4 | **每换一个 Agent 就要重新解释**意图、偏好、判断标准、授权习惯 | 用户本人 |
| 痛点 5 | 开源能力分散，用户像无头苍蝇满世界找"最佳方案" | 想升级的用户 |
| 痛点 6 | 省 token / 外部审查 / 浏览器自动化各家分散，且成本口径不诚实（"免费"≠真免费） | 成本敏感用户 |
| 痛点 7 | AI 操作软件靠截图/DOM/坐标，不可回放、不可审计、UI 一改就全废 | Agent-native |
| 痛点 8 | 并行开发缺隔离：CLI/API/MCP 多项目并行互相串味、抢资源 | 并行开发 |

## 3 · 核心理念（每条：理念 / 为什么 / 落地 / 可被推翻条件）

### P1 · 人主导、AI 辅助，同一工作台
人是创作主体，AI 是放大器；人和 AI 共用同一工作区、session、权限、时间线。
- 为什么：解决痛点 1（拼接式割裂）。
- 落地：`docs/01`、`docs/02`、`docs/18`。
- 可被推翻：若证明"全自动无人值守"才是用户真实需求且可控——目前不是（见 §6 非目标）。

### P2 · Agent-native：人和 AI 用同一套结构化动作
每个内部写能力 = 一条 `InternalActionDefinition`（schema + 权限 + timeline + undo）；人点按钮和 Agent 调工具走**同一个 action id**。
- 为什么：解决痛点 7（截图/DOM 不可回放）。这是 Fleet 的承重墙。
- 落地：`docs/40`（注册表）、`app/.../protocol/internal-action.ts`（代码即契约）、`docs/38`（方向）。
- 可被推翻：几乎不可——这是与"套壳工具"的根本区别。

### P3 · 一条脊柱，不建第二套
session / permission / timeline / actor 身份是唯一真相；所有能力适配进 craft，不另起第二套会话/记忆/权限。
- 为什么：避免状态分裂（痛点 1/3）。
- 落地：`AGENTS.md` 规则 13、`docs/30/31`。
- 可被推翻：若 craft 脊柱被证明无法承载某关键能力——目前未出现。

### P4 · 能力管理是第一公民：安装/装载/运行三分离
目录全量、装载最小、运行隔离。Agent **自主**为自己和队员装载最小能力集，按工作区/身份/任务隔离。
- 为什么：解决痛点 2/8（能力爆炸 + 注意力有限 + 跨项目串味）——这是用户认定的"真正大问题"。
- 落地：`docs/43`（D25）、`docs/17 §3.2`（身份裁剪）、`docs/04 D25`。
- 可被推翻：若用户改为"人工精选一次、全程固定"——但那正是别人做不好的旧路。

### P5 · 双层 Agent + 身份分离：管理 Agent 是"第二分身"
管理 Agent（软件管家，沉淀用户偏好/判断/授权习惯）≠ 队长（项目工头）≠ 队员（专业执行）；身份分离、同一条 timeline。
- 为什么：解决痛点 3/4（大项目要分工，又不能让管理 Agent 被微观工具耗尽带宽；让"第二分身"记住用户、免重讲）。
- 落地：`docs/17`（D11/D12）、`docs/33`（团队脊柱）。
- 可被推翻：若双层带来的协调成本 > 收益——用单进程逻辑隔离 + 身份裁剪控制成本（已采纳）。

### P6 · 记忆是飞轮，不是只读笔记
分区分层记忆；程序记忆绑定 Skill/internal action；成功轨迹蒸馏成 Skill，下次检索复用并驱动**能力装载**。越用越懂用户、越会用工具。
- 为什么：解决痛点 4（免重讲）+ 让 P4 的自主装载"越来越聪明"。
- 落地：`docs/05`（D2，含 §4.1 飞轮）。
- 可被推翻：若本地记忆检索收益不足——保持接口隔离、可关闭回退原样。

### P7 · 防过度工程化：单进程逻辑隔离优先
多 Agent 隔离优先用身份裁剪 + 命名空间 + 注入 env + 租约；物理沙箱/常驻 Daemon/Portal 是 M3 条件项，不是落地前置。
- 为什么：避免在主干就绪前堆重基础设施（痛点 3 的反面教训）。
- 落地：`docs/42 §1.2E/§2`、`docs/04 D22`。
- 可被推翻：出现真实"GUI 关闭后仍要后台长程任务"需求时，才升级 Daemon/沙箱。

### P8 · 集成 vs 兼容 + 自带最佳组合
长期稳定/基础性/绿灯 → 直接集成；迭代快/靠社区 → 做兼容(adapter/BYO/sidecar)。Fleet 预配每类能力的最佳组合，替用户省选型成本。
- 为什么：解决痛点 5（满世界找）+ 享开源红利又不被许可证漂移拖累。
- 落地：`docs/04 D24`、`AGENTS.md` 规则 42、`docs/29 §1.5`、`docs/16 §4`。
- 可被推翻：单项目判定可调整，框架本身稳定。

### P9 · 诚实与可回放
真实 / 估算 / 未知必须分列；一切写操作可审计、可撤销、有依据。
- 为什么：解决痛点 6（虚假省钱/免费）+ 建立信任。
- 落地：`AGENTS.md` 规则 21/23、`docs/16`、`docs/40`。
- 可被推翻：不可——这是产品诚信底线。

### P10 · 合规红线：不绕、不偷、不冒充
不绕用量/风控/检测/验证码/配额，不 stealth，不账号轮换规避，不读 cookies/token；绿灯才迁源码，红黄灯只黑盒。
- 为什么：合法可持续；解决痛点 6 的"灰色诱惑"。
- 落地：`AGENTS.md` 规则 3/4/17/22、`docs/04 D4/D10/D23`。
- 可被推翻：不可——红线。

### P11 · 多工作面共享脊柱、原生引擎各异
默认工作台 + 无限画布 + AIGC + 网页/文档 + 视频剪辑：共用项目/素材/Agent/记忆/权限/timeline/账本，但各用适合自己的原生引擎，不强塞一个万能格式。
- 为什么：真实生产流程一站完成（愿景），又不牺牲专业度。
- 落地：`docs/18`、`docs/02`、`docs/30/31`、`docs/15`。
- 可被推翻：单个工作面的引擎选型可换（受绿灯约束）。

### P12 · 第二分身沉淀用户思想（本白皮书自身的理由）
用户的愿景、判断标准、偏好、洞察必须沉淀成可复用真相，让任何 Agent 不必重讲就能对齐并审优。
- 为什么：解决痛点 4 的根源——这正是本白皮书存在的意义。
- 落地：**本文** + `docs/05`（记忆）+ `docs/04`（决策）。
- 可被推翻：不可——这是项目能被多 Agent 持续优化的前提。

## 5 · 评审协议：Agent 怎么审"是不是最优"（而非盲目执行）

> 用户要求：Agent 要能更好地审核"现在的方案是不是最佳路线、有没有更好的方法"，而不是一味执行。

任何 Agent 在**优化方向 / 选型 / 新增能力**前，必须先回答三问，并写进交付说明：

1. **服务哪条理念？** 这步对应 §3 的哪条 P？不对应任何理念 = 可能跑偏，先停。
2. **是不是最优？** 列出至少一个替代方案 + 取舍（成本/风险/可回放/许可证/与脊柱契合度）。如果当前方案不是最优——
3. **更优解怎么落？** **先改本白皮书理念 / 或 `docs/04` 决策**（留依据），再改下游实现；不得只改代码而让理念与实现脱节。

硬约束：
- 不得违背 §3 理念清单与 P10 红线。
- 发现理念之间冲突，升级给用户拍板，不自行二选一。
- "某 Agent 说完成/最优"不算数；以本机 diff / 测试 / 与理念一致性为准（`AGENTS.md` 23）。

## 6 · 非目标（明确不做，省得反复被"带偏"）

- ❌ 不做"多 CLI Agent 管理器"为终点（CLI 只是入口）。
- ❌ 不做绕用量/风控/检测/验证码/配额、不做 stealth/反检测、不做账号轮换规避（P10）。
- ❌ 不做无人值守的全局录屏/监控为主路径（录制必须显式、可停、语义优先）。
- ❌ 不在主干就绪前堆 Daemon/物理沙箱/云会员网关（P7，M3 条件项）。
- ❌ 不把第三方未绿灯源码 vendor 进 `app/`（P10）。
- ❌ 不为新功能另起第二套 session/记忆/权限/UI 壳（P3）。

## 7 · 与文档体系的关系 + 收束目标

- 本文是 **WHY 北极星**；`docs/README.md` 是导航；`docs/00 §7` 是文档收束（多文档 → 闭环套件）的执行计划与状态。
- **文档收束的目标也服务本白皮书**：收束后每个"闭环套件"文档都应能在 §4 追溯表里找到它落地的理念；找不到归属的文档就是收束候选。
- 收束纪律见 `docs/00 §7.3`：逐套件迁移、删除即更新引用、仓库始终自洽，不大爆破。
- 理念有变 → 改本文 → 同步 `docs/04` 决策 → 下游文档跟随（`AGENTS.md` 规则 35）。
