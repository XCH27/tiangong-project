# 02 · AI 工作创作台与统一交互模型（产品定义）

> 状态日期：2026-06-22
> 最新校准：软件开发、内容创作和 AIGC 只是代表性场景，不是产品边界。默认工作台与无限画布、AIGC、网页/文档、视频剪辑四个专业工作面共享“我的工作区”、本地素材、Library、Agent、记忆、权限、timeline 和成本账本。
> 对应决策 **D13 统一创作台定位**（见 `docs/04-产品决策记录.md`）。
> 定位：定义 Fleet 是什么、为什么一个软件能同时服务多种创作场景、人和 AI 怎么在同一套界面里协作。它是 `docs/01` 主干的"产品哲学层"，是 `docs/18` 目标态 UI 的"为什么这么设计"。
> 关系：产品定位与交互模型在本文；路线排序在 `docs/01`；具体目标态界面在 `docs/18`；决策真相在 `docs/04`；铁律在 `AGENTS.md`。

## 1 · 一句话定位

**Fleet 是一个"AI 工作创作台"：人类主导、AI 辅助，人和 AI 在同一个软件里完成真实生产流程。**

它**不是**：聊天工具、IDE、浏览器自动化工具、Figma 克隆、视频剪辑软件中的任何单一一个。
它**是**：把这些场景需要的能力（画布、时间线、属性面板、素材库、版本记录、AI 指令、导出）收进**一个结构化工作台**，让真实工作端到端发生在软件内部，而不是散落在桌面、浏览器和一堆外部软件之间。

产品核心不是"AI 帮我聊天"，而是"**人和 AI 在同一个创作台里完成真实工作**"。

## 2 · 关键差异：把场景收进来，而不是接管桌面

Hermes、OpenClaw 这类项目的思路是让 Agent 去**接管外部桌面 / 浏览器 / 一堆复杂软件**——在混乱的桌面环境里到处找按钮、切窗口、识别页面。它强大，但脆弱、耗 token、难记录回放。

Fleet 反过来：**把常用生产场景尽量收进软件内部，做成结构化工作台**。带来的好处：

| 维度 | 接管桌面（Hermes/OpenClaw 路线） | 收进软件（Fleet 路线） |
|---|---|---|
| Agent 操作对象 | 屏幕像素、外部窗口、识别页面 | 结构化 Stage / Inspector / Library / Timeline / Action |
| 稳定性 | 受外部软件版本/布局影响，易碎 | 软件自己定义的稳定结构 |
| token 成本 | 反复截图识别、找按钮 | 结构化动作，省上下文 |
| 记录/回放/授权/回滚 | 难 | 每个动作进 session timeline，可授权可回滚 |
| 人机协作 | Agent 单干为主 | 人和 Agent 共用同一套选区与动作 |

**边界**：外部桌面/浏览器/外部网站不是默认操作面，而是**例外**——只在真实网页标注、外部 AI 审查提交等明确场景，通过 craft BrowserPane / `browser_tool` 受控进入（见 `docs/06`、`docs/16`、`AGENTS.md` 规则 22）。绝不把"在混乱桌面里替人点按钮"当默认能力。

## 3 · 统一洞察：多场景不是多软件，是同一工作台的不同配置

三类旗舰场景看似不同，其实是**同一个生产闭环 + 同一套基本件**的不同配置：

### 3.1 同一个生产闭环

每个场景都是这条闭环：

```
输入需求/意图 → 生成 → 编辑/调参 → 挑选素材 → 标注问题 → AI 修改 → 审查版本 → 导出交付 → 发布上线
```

每一步都是一个 Surface 动作，都产生 session timeline 事件，都可被人或 AI 触发。

### 3.2 同一套基本件（工作台由这些组成，不是由"每个场景一套 UI"组成）

| 基本件 | 是什么 | 在 craft 的落点 |
|---|---|---|
| **Project（项目）** | 有类型的容器（软件 / 内容 / AIGC / 混合）。项目类型配置可用专业工作面、Agent、素材库和导出目标。持有时间线、素材、版本、记忆分区和权限档。 | session/workspace + 记忆项目分区（`docs/05`） |
| **专业工作面** | 默认工作台、无限画布、AIGC、网页/文档、视频剪辑是同一软件的不同工作面。重交互功能先在独立工作面跑通，不强塞进默认聊天页。 | `docs/18` |
| **工作面自己的属性与选区** | 每个工作面使用适合原生引擎的选区、属性面板和编辑操作；统一的是 actor、permission、timeline、资产引用和工具动词，不是一个通用 Inspector 解释所有内容。 | `docs/30`/`docs/31` |
| **Library（素材库）** | 统一资产库：媒体 / 组件 / 模板 / 字体 / 色板 / 动效 / 代码片段 / prompt / 片段。来源/许可证/hash 可追踪，拖入 Stage。 | `DesignLibrary` service |
| **版本/历史** | 各原生引擎管内容级撤销/版本；Craft session timeline 记录谁在什么工作面做了什么、权限和原生回放句柄。 | SessionEvent + 原生 history |
| **导出/发布** | 有类型的导出目标：部署代码 / 渲染视频 / 导出 HTML·Figma / 上传平台。都走 permission + 记录。 | Handoff + 审查中心 |
| **AI 指令通道** | **一个**输入框，按上下文路由（见第 4 节）。 | Conversation 输入区 |

### 3.3 时间线的两义（必须区分，别混淆）

- **会话时间线（脊柱）**：事件日志——谁做了什么、为什么、用什么工具、权限、回滚。就是 craft 的 `SessionEvent` 流。**所有场景共用这一条。**
- **媒体/编辑时间线（Stage 的一种模式）**：动画/视频/分镜的轨道/关键帧/片段编辑面。它是 Stage:Timeline 模式。
- **二者的关系**：在媒体时间线上的编辑，产生 `DesignAction`，落到会话时间线脊柱上。所以编辑时间线也是 agent-native、可回放、可回滚的。

## 4 · 统一输入与路由模型（核心交互）

每个工作面保留一个语义一致的主输入入口，软件按上下文路由到合适的 Agent / 工具 / 编辑通道。路由依据：**当前选区 + 当前工作面 + 当前项目类型 + 上下文/记忆**。这不要求所有专业页共享同一个 React 输入组件，只要底层语义和路由契约一致。

| 用户说 | 当前选区 | 当前工作面 | 路由到 |
|---|---|---|---|
| "把这个按钮调大一点" | 选中按钮 | Design Canvas | `set_style` DesignAction（人/AI 同通道） |
| "把这段动画变快" | 选中片段/关键帧 | Timeline | 时间线 op（duration 缩放） |
| "把这个分镜改成夜景" | 选中分镜格 | Board | 设计 Agent 重生成该格图 |
| "审查这个项目并列出风险" | 无选区 | 项目级 | 审查 Agent + 上下文效率/审查中心（`docs/16`） |
| "把这几个视频片段合成一个作品" | 多选片段 | Compositor/Timeline | 合成 Agent + timeline assemble + 导出 |
| "这段后端接口实现一下" | 选中函数/文件 | Code | 代码 Agent + 代码 patch |

**关键**：统一输入和 `DesignAction` 是一体两面——同一个被路由出的动作，既能由人打字触发，也能由 Agent 调结构化工具触发。所以"统一输入框"天然 agent-native：人说的话和 Agent 的工具调用进同一条路由、同一条 timeline、同一套权限与回滚。

路由器本身要诚实：解析不出明确目标时，回到 Conversation 让用户澄清或选择，而不是猜一个危险动作执行。

## 5 · 人类主导，渐进自动化

- **默认人类主导**：用户可手动设计、编辑、拖拽、标注、调参；也可随时让 Agent 接着做。Agent 是辅助者、执行者、整理者、自动化操作者，不是默认主导。
- **渐进开放自动化**：使用时间够长、管理 Agent 足够了解用户偏好/项目规则/常用判断/软件能力后，用户**可选择**开启更高自动化，让 Agent 在授权范围内代替人做判断和操作。
- **分级**：对齐 `docs/16` D12——L0 只读自动 / L1 低风险本地按偏好 / L2 写入·运行·外发需授权 / L3 删除·发布·付款·登录·敏感必须确认。每个自动判断有依据、有记录、可回放、可撤销。
- **永不**：默认 Agent 主导、自动同意 L3、把"开了自动化"当无限授权。

## 6 · 三场景映射（"不割裂"的证明）

同一个生产闭环和底层脊柱，不同工作面 / Agent / 素材配置 / 导出目标由项目类型配置：

| 生产步骤 | 软件开发 | 内容创作（视频/动画） | AIGC（小说→短视频） |
|---|---|---|---|
| 输入需求 | 需求 / PRD | 脚本 / 分镜需求 | 小说 / 剧本 / 设定 |
| 生成 | 前端/后端代码、页面 | 动画 / 素材生成 | 分镜图 / 片段生成 |
| 编辑/调参 | 页面编辑(Design Canvas)、代码(Code) | 逐帧/关键帧(Timeline) | 分镜编排(Board)、片段(Timeline) |
| 挑选素材 | 组件/模板库 | 媒体/音频库 | 分镜/片段库 |
| 标注问题 | 代码注释/页面标注 | 帧/片段标注 | 分镜标注 |
| AI 修改 | 改代码/改样式 | 重渲染/调速 | 重生成分镜/片段 |
| 审查版本 | 代码审查/回归 | 预览/版本对比 | 成片审查 |
| 导出交付 | 部署/上线 | 渲染导出/上传 | 合成成片/上传 |

**结论**：这是一个软件，不是几个孤立 app。每个场景共用工作区、本地素材/Library、会话时间线、版本、导出、Agent、记忆、权限和 token 账本；各专业工作面保留适合自己的布局和原生引擎。

## 7 · 这不改变建造顺序（重要约束）

本文是**北极星愿景**，不是 M0 任务清单。建造顺序仍以 `docs/01` 为准：

- **先建底座**（M0）：动作引擎 `DesignAction→Patch→SessionEvent`、浏览器 docked 画布、Usage/Token 账本、CLI 接入收口。统一输入路由、Design Canvas 是第一批落到这个底座上的。
- **再加专业工作面**（M1–M2）：无限画布、AIGC、网页/文档、视频剪辑逐一跑通原生编辑和 Agent 工具闭环。
- **Timeline / Board / Compositor（视频·动画·AIGC 编辑）是 M2 主线**：先完成团队脊柱、全部文件/Library 和最小原生引擎契约，再分别跑通专业工作面；不自研完整 NLE，也不将它们无限延后。
- 视频导出仍受 HyperFrames/Remotion/Kdenlive 许可证边界约束（`docs/14`），先做网页动效（CSS/WAAPI/SVG/Lottie），不自研完整 NLE。

一句话：**愿景是统一创作台，但仍是共享底座先行、专业工作面逐个跑通，不重做默认界面。**
