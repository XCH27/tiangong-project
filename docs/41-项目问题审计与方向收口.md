# 41 · 项目问题审计与方向收口（梳理结论 · 接手必读）

> 状态日期：2026-06-25
> 用途：一次系统梳理后，把**当前文档/代码里阻碍落地的问题**和**唯一确定的下一步方向**收口成一页。接手的智能体先读本文，再读 `docs/40`（执行规格），就能精准落地，不会在三套“下一步”里打转。

## 0 · 一句话方向（重申，作为收口锚点）

**Fleet 不做“多 CLI Agent 管理器”。CLI / ACP / MCP 只是入口和外部桥。Fleet 的差异化 = 让 Agent 低 token、高安全、可回放地操控软件内部的结构化生产能力。** 别人让 Agent 操作外部世界（网页/桌面/终端）；Fleet 把生产能力收进固定软件环境，让 Agent 操作**结构化对象和 internal action**，而不是操作屏幕。

这条已经在 `docs/38`、`docs/04 D14a`、`AGENTS.md 规则 19a` 写定，本轮梳理确认它**正确且应作为后续主线**。问题不在方向，而在“方向已写、但落地路径被三套相互矛盾的叙述和两套相互冲突的类型定义挡住”。

## 2 · 发现的问题（P1–P8）

> 排序：P1–P3、P8 是阻断“落地新方向”的硬问题；P4–P5 是文档卫生；P6–P7 是精度与执行闭环。

### P1 · 核心类型有两套冲突定义（最高优先级）【已改 → 收口到 `docs/40`】

- 现象：同一个“内部 action 类型”，`docs/38 §4` 叫 `InternalActionDefinition`（字段 `id / surface / action / agentCallable / humanEntryPoints / requiredCapabilities / contextSummary`），`docs/39 §5.1` 叫 `FleetActionDefinition`（字段 `actionId / surface / title / locality / replayPolicy / redactionPolicy`）。**字段名不同（`id` vs `actionId`、`action` vs `title`）、字段集不同、surface 取值也不同。**
- 为什么阻塞：实现 Agent 无法判断该按哪套建表。这是用户点名要做的 #2（Internal Action Registry）的承重墙，定义二义=直接返工。
- 处置：本轮新建 `docs/40 §2` 合并两版为**唯一** `InternalActionDefinition`（统一 `id`，吸收 locality/replayPolicy/redactionPolicy/contextSummary，补 `verb`/`undoHandle.noneReason`）。38/39 的草案降级为“以 40 为准”。

### P2 · surface 取值有三套，互不一致【已改 → 收口到 `docs/40 §3`】

- 现象：`design.ts` 代码里 `WorkbenchSurface = browser|artifact|code|document|timeline|board`；`docs/38` 用 `default-workbench|canvas|aigc|web-doc|video|files|settings`；`docs/39` 用 `session|browser|terminal|file|design|aigc|video|settings|skill`。
- 为什么阻塞：注册表的 `surface` 字段没有唯一词表，Agent 跨面心智不统一，Skill/Recorder 无法稳定按面过滤。
- 处置：`docs/40 §3` 定唯一 `ActionSurface` 词表，并给出 `design.ts` 对象枚举 → `ActionSurface` 的映射表（区分“对象在哪个原生面”和“action 属于哪类能力”）。

### P3 · 有三套相互矛盾的“下一步”，没有收口（最容易让接手 Agent 跑偏）【已改 → 见 §3】

- 现象：
  - `docs/00 §2` + `docs/01 §8` + `docs/33`：下一步 = **团队脊柱前端**（A1/A2）。
  - `docs/30 §11` + `docs/31 §10`：下一步 = **脊柱瘦身（已完成）+ 设计面 re-base openpencil（S2）**。
  - `docs/38 §10` + 用户本轮指令：下一步 = **补 Internal Action Registry + 一个 surface 的样板闭环，不要继续堆 UI**。
- 为什么阻塞：三个入口文档把读者导向三件不同的事。读 00/01/33 会去做团队 UI；读 30/31 会去 vendor openpencil（且被许可证绿灯阻塞）；读 38 才会去做注册表。
- 处置：用户本轮已明确“下一步优先做样板闭环，不要堆 UI”。本轮把 `docs/00 §2`、`docs/01 §8` 的“当前最高优先级/下一步”统一改写为 **Internal Action Registry 样板闭环优先**，并把团队前端、openpencil 重新排到它之后/旁路（openpencil 仍被许可证绿灯阻塞，不变）。收口后的唯一序列见 §3。

### P4 · Skill manifest 重复定义且漂移【已改 → 唯一定义在 `docs/39 §5.7`】

- 现象：`FleetSkillManifest` 在 `docs/38 §6` 和 `docs/39 §5.7` 各定义一次，字段有差异（38 有 `requiredExternalJobs` 与 `replay.preferred`，39 没有）。
- 处置：以 `docs/39 §5.7` 为唯一定义（补回 `requiredExternalJobs`）；`docs/38 §6` 改为引用，不再重复贴整段类型。`docs/40 §8` 也指向这一处。

### P5 · 状态真相分散且自相矛盾【已改 → 状态唯一真相归 `docs/32`】

- 现象：原 13 号维护文档把“当前分支完成状态”同时指给 `docs/00` 和 `docs/32`；二者日期不同（00 是 06-22，32 是 06-24）且结论冲突。更严重的是 **`docs/00` 自身矛盾**：第 19 行把“管理 Agent 分级自动决策 L0-L3”标为 `✅ 已落主线`，第 24 行又把同一能力标为 `🟡 候选/待合入（未提交主线）`。
- 为什么阻塞：状态是“能不能依赖某能力”的判断依据，自相矛盾会让接手 Agent 误判已落/未落。
- 处置：本轮把**状态唯一真相收敛到 `docs/32`**（最新、结构化、有文件所有权）；`docs/00` 删除自相矛盾的重复条目，改为“当前事实摘要 + 指向 `docs/32`”，不再维护第二份长状态表；原 13 号维护文档的真相分工同步改为“当前状态只认 `docs/32`”（该文档已并入 `README`）。

### P6 · 注册表无代码，且存在命名撞车风险【已处理 S1 → 后续登记其它能力】

- 原现象：`InternalAction` / action registry / action bus 无实现；唯一叫“registry”的是 renderer 的 `actions/registry.tsx`（键盘快捷键/命令注册表），存在建错层风险。
- 已处理：S1 已新增 `shared/protocol/internal-action.ts`、`server-core/services/internal-action-registry.ts`、`internal-action-executor.ts`、`file-mutation-service.ts`、`handlers/rpc/internal-actions.ts`，并与 renderer hotkey registry 显式区分。
- 剩余：把已落的其它内部能力逐个登记进 S1 注册表，避免继续保持散点工具/散点按钮。

### P7 · “少即是多”是原则，但没有执行闭环【已改 → 接进自检清单】

- 现象：`docs/38 §8` 写了“少即是多”，但没有任何检查把它变成可执行动作。
- 为什么重要：用户点名的 #7（页面用“少即是多”降低 Agent 操控难度与 token）必须落到“删/灰掉没有真实 action 的按钮”，否则只是口号。
- 处置：注册表天然提供判据——**一个写按钮如果在注册表里找不到对应 action，就是删除或 disable 的候选**。本轮把这条接进 `docs/00A §6` 提交前自检清单（新增一条），让它成为硬门。

### P8 · 新 `InternalAction` 与现有 `DesignAction` 信封的关系未定义【已改 → `docs/40 §4`】

- 现象：`design.ts` 是“动作信封单一真相/承重墙”，38/39 又引入新 `InternalAction` 类型，但**没人说清二者是不是一回事**。
- 为什么阻塞：不说清，实现 Agent 会再造第三套平行结构，违反“不建第二套真相”。
- 处置：`docs/40 §4` 定死关系——**注册表 = 静态目录；`DesignAction` = 一次动态调用**；二者是同一动作的两面。工程上已明确拆分：`DesignAction.actionId` 保持 invocation/patch id，新增 `actionDefinitionId?`/`contractVersion?` 引用注册项；`DesignEngine` 注入注册表，复用现有 `DesignAction → DesignEngine → SessionEvent → DesignPatch` 链路，不新增执行链。

### P9–P15 · 外部审查补充修正（2026-06-25 · 已并入 `docs/40`）

一次外部 Agent 审查在实现前又发现 `docs/40` 三处 P0、三处 P1（外加记忆域一处）。前三处不修正，第一个 `files` 闭环会把权限与对象模型做错。已全部并入重写后的 `docs/40`：

| 编号 | 现象 | 处置（`docs/40`） |
|---|---|---|
| **P9（P0）对象模型自相矛盾** | `files.select_entry` 产出 `WorkbenchObjectRef{surface:'browser'->files}`，但 `WorkbenchSurface`（design.ts:90）无 `files`、且映射规定 `browser->web-doc`，让文件伪装成浏览器选区 → 权限/回放/过滤漂移 | §4.1 抽出通用 `ActionTargetRef`（surface∈`ActionSurface`），files 用 `{surface:'files',kind:'file'}`，不复用 Stage 选区 |

| **P11（P0）文件移动/撤销不安全** | `fromPath/toPath` 无根约束/规范化/symlink 防逃逸、无不覆盖/源 hash/撤销前目标未变前置条件；路径默认非敏感 | §6.3 补六条安全约束 + `ActionInvocation` 的 `preconditions`/`idempotencyKey`/`failurePolicy`；`redactionPolicy` 含路径 |

| **P13（P1）缺版本/迁移/前置条件** | 只存一次调用 id，UI/schema 演进后旧流程无法定位契约版本或判断目标是否仍适用 | §2 增 `contractVersion`/`deprecates`/`replacedBy`/`payloadMigrations`；§2.1 把它定为“界面变、动作用迁移函数跟着变”的工程落点（正是用户原始诉求） |

| **P15（P1）记忆缺可配置 Embedding 方案** | `docs/05` 只写“未来本地向量索引”，未定义文本/视觉 embedding 分流、默认本地 Provider、远程 API 显式授权、Keychain、按七域隔离索引、删除联动、重建与召回证据 | **排进记忆能力域**（见 §4 收束计划）；`doubao-embedding-vision` 作为**可选视觉检索 Provider**，不是记忆事实源、不是默认云依赖 |

## 3 · 收口后的唯一“下一步”序列（替代三套矛盾叙述）

> 本节是 §2 P3 的收口结果，也是 `docs/01 §8`、`docs/00 §2` 改写后的指向。

**主线只有一条：先把“内部能力”收进注册表，再让创作面和团队前端挂上去。**

1. **【当前 S1 候选】Internal Action Registry + `files` 样板闭环。** 已按 `docs/40` 落到当前工作区：唯一类型 + 唯一 surface 词表 + 四条 `files` action（inspect/select/edit/undo）+ 两个通用 Agent 工具（`list/invoke_internal_action`）+ permission/timeline/undo 接线 + Files 面板代码接线。人工视觉点验、提交主线并复核后，`docs/32` 可升 ✅。
2. **【紧接】盘点并注册现有内部能力。** 把已落的散点能力（files 只读、team、progress、status、labels、memory、browser selection）逐个登记为注册表条目，使“人类按钮 ↔ Agent 工具同一 action”在全项目成立（`docs/38 §10` 第 1 步）。这一步**不写新 UI**，只把已有能力“收进注册表”。
3. **【再做 · 每个新按钮必须带 action】团队前端（A1/A2）与其它增量 UI。** 团队后端已基本落（`docs/32`），剩前端；但前端每加一个写按钮，必须在注册表里有对应 action，否则按 P7 自检 disable。`@`/`/` 输入迁移、会话列表团队化属于此层。
4. **【许可证绿灯后】创作面原生引擎。** 设计面 re-base openpencil（S2）、视频面 opencut-classic（S6）等仍**被许可证绿灯阻塞**（`docs/30 §12`、`docs/31 §11`），不在前三步之前做；解锁后它们各自以“注册成 Internal Actions”的方式挂上脊柱，不是另起一套。
5. **【横向】Workflow Recorder / Skill Distiller。** 按 `docs/39`，在注册表跑通后旁路监听 action 调用蒸馏 Skill；它依赖第 1–2 步的注册表，不能先于注册表做。

为什么是这个顺序：注册表是“把生产能力收进内部”的承重墙，第 2–5 步全部挂在它上面。先做它，后面每一步都自动获得“人机同源 + 低 token + 可回放 + 可撤销 + 有权限”；不先做它，团队 UI 和创作面会继续堆出“只有人能点、Agent 要截图”的暗状态，正是方向要消灭的。
