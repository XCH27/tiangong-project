# 19 · 新基座重做资产与边界清单

> 状态日期：2026-06-20
> 目的：定义干净 craft-agents-oss 基座上应重做哪些能力，以及哪些旧二开形态不再迁移。

## 1 · 当前判断

当前 `app/` 已重置为干净 craft-agents-oss。旧二开代码不再作为源码来源，只保留产品判断和少量可重做能力边界：

- **可重做能力**：CLI Runtime/ACP、动作信封/选区描述、团队脊柱、全部文件/Library、Usage/Context Report 和专业工作面。
- **不迁移形态**：旧 renderer local state、旧设计侧栏、旧聊天区拼接 UI、旧过程性 smoke/快照记录。

下一轮路线：

1. 先确认当前干净 craft 基座能安装、typecheck、启动。
2. 在 craft 原结构内小步重做 CLI Runtime/ACP。
3. 再在 Craft 原结构内收敛团队脊柱和全部文件/Library；不重做默认壳。
4. 所有 UI 从干净基座实现，不从旧 UI 复制。

## 2 · 必须重做

### 2.1 CLI Runtime / ACP

这是旧二开里最有价值的产品方向，但代码不再直接迁移。新实现必须重新接 craft 的 session、permission、timeline 和 RPC。

重做范围：

- `packages/server-core/src/services/cli-runtime-acp-client.ts`
- `packages/server-core/src/services/cli-runtime-acp-adapter.ts`
- `packages/server-core/src/services/cli-runtime-acp-event-mapper.ts`
- `packages/server-core/src/services/cli-runtime-adapter-registry.ts`
- `packages/server-core/src/services/cli-runtime-catalog.ts`
- `packages/server-core/src/services/cli-runtime-detected-acp-mappings.ts`
- `packages/server-core/src/services/cli-runtime-launch-diagnostics.ts`
- `packages/server-core/src/services/cli-runtime-process-registry.ts`
- `packages/server-core/src/services/cli-runtime-send-resolver.ts`
- 对应测试与 `fake-acp-cli` fixture

实现方式：

- 先写 pure/service 文件和测试。
- 再接 shared DTO/channel/routing 中的 CLI Runtime 字段。
- 最后接 RPC handler、input popover 和 settings 页面。
- 每一步都跑对应测试，不做整包覆盖。

### 2.2 CLI Runtime 表单与错误态 helper

可迁移：

- `components/cli-runtime/cli-runtime-form-helpers.ts`
- `components/cli-runtime/__tests__/cli-runtime-form-helpers.test.ts`
- `renderer/lib/cli-runtime-models.ts`

谨慎迁移：

- `CliRuntimePanel.tsx` 只迁逻辑和状态文案，不原样继承视觉结构。

## 3 · 重做契约，不迁 UI 形态

### 3.1 DesignAction / selection 机制

这些可以作为未来专业工作面的选区与动作信封参考，但不从旧 `app/` 复制：

- `renderer/lib/design-action.ts`
- `renderer/lib/__tests__/design-action.test.ts`
- `renderer/components/preview/design-preview-helpers.ts`
- `renderer/components/preview/__tests__/design-preview-helpers.test.ts`
- `renderer/lib/design-overlay-script.ts`
- `resources/design/select-mode-overlay.js`

重做原则：

- 只迁纯函数、类型思路和 iframe/selection 通信机制。
- UI 必须从 Craft 原界面原位修改；重交互能力只在确有需要时新建专业工作面。不再建 `WorkbenchShell`。
- renderer-only mutation 不能作为最终方案。
- 新实现必须把人类 UI 和 AI tool 汇入同一套 `Action -> Patch -> SessionEvent`。

## 4 · 需要在新基座重做的能力

以下能力需要重新实现，而不是直接复制界面形态：

- 默认工作台：保留 Craft 会话、列表、标签、设置和 BrowserPane 的原结构，只做必要字段与入口增量。
- 专业工作面：无限画布、AIGC、网页/文档、视频剪辑各用原生引擎与自己的属性/时间线，共用底层脊柱和本地素材。
- `DesignAction -> DesignPatch -> SessionEvent` 后端闭环，替代临时 renderer 状态。
- `Comment AI` 与证据包：选择、框选、多选、截图、DOM/AX 摘要、批量注释。
- `Usage/Context Report`：真实 token、估算节省、外部平台成本、bundle hash、secret scan。
- 管理 Agent / 项目 Agent 身份元数据、权限卡和会话 timeline 回放。
- `dist/`、`.DS_Store`、`node_modules`、临时 smoke 输出。

## 5 · 新基座第一批落地顺序

1. **干净 craft 基座启动**：install、typecheck、electron dev。
2. **CLI Runtime / ACP 重做**：先 service/test，再 shared/RPC，再 UI 入口。
3. **团队脊柱**：原标签扩展身份能力，团队状态、队长唯一性、群聊特殊会话和管理 Agent 边界进入原 session/permission/timeline。
4. **全部文件 / Library**：建共享本地素材与资产来源层。
5. **专业工作面**：按无限画布、AIGC、网页/文档、视频剪辑分别跑通最小闭环，不更换 Craft 默认界面壳。

## 6 · 判断标准

一个模块能否进入新基座，必须同时满足：

- 能独立说明它解决什么问题。
- 有测试或实机验证。
- 不依赖不可回放的 renderer-only 状态。
- 不引入第二套 session、permission、memory 或 browser stack。
- 能放进 `docs/01` 的主干顺序里。

不满足就不迁，改为在新基座按路线重新实现。
