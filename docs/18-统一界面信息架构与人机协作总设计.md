# 18 · 统一界面信息架构与人机协作总设计（目标态）

> 状态日期：2026-06-22
> 定位：这是 Fleet 在**愿景中所有功能都实现后**应该长成的界面与交互的单一总设计。它回答三个问题：整个 UI 应该是什么样、人怎么用、agent 怎么用。
> 产品定义前置：本文是"目标态 UI 真相"，它实现的是 `docs/02-统一创作台与交互模型.md` 描述的 AI 工作创作台——同一套界面服务软件开发 / 内容创作 / AIGC 三类场景，Stage 是一个画布多种模式（Code/Canvas/Browser/Timeline/Board），统一输入按上下文路由。
> 关系：`docs/02` 是产品定义/交互模型，`docs/15` 是功能愿景，`docs/06` 是浏览器标注路线，`docs/19` 是新基座迁移边界。本文只描述目标态与分阶段落点。
> 最新校准（2026-06-22）：保留 craft 默认工作台，并增加无限画布、AIGC、网页/文档、视频剪辑四个专业工作面。它们共享本地文件、Library、Agent、权限和 timeline。下文五个 Surface 是工作台内部布局原则，不表示所有专业能力必须挤在一个三栏页面里。

---

## 0 · 为什么这是最难的部分

Fleet 要在**一个窗口**里同时承载：与 API 模型/本机 CLI(ACP) 对话、真实浏览器(BrowserPane/CDP) 兼网页设计标注、Artifact Studio(编辑 AI 生成的网页/APP/PPT/商品页)、资源库(媒体/组件/模板/字体/色板/动效)、字体/颜色/动画编辑、Figma/Stitch 交接、上下文用量+项目打包+外部 AI 审查、分级记忆、多 Agent 编排、手动编辑逃生舱。

难点不在"功能多"，而在两个结构性约束：

1. **它们不是 12 个独立 app，而是同一条 session timeline 的不同视角。** 任何把它们做成 12 个孤岛页签的方案都会在第 3 个功能时崩塌——状态分裂、上下文丢失、agent 无法跨面操作。
2. **同一套界面要被人和 AI 同时操作。** craft 的核心哲学是软件本身可被 AI 编辑。所以 UI 不是"人类编辑器 + AI 聊天框"，而是一个**人和 agent 共编的工作台**：每个人类控件都要有等价结构化动作，每个 agent 动作都要在同一界面里可见、可审批、可回放。

因此本设计的核心不是"画好看的面板"，而是定义**少量持久 Surface + 一条共享时间线 + 一套人机对等的动作模型**，让所有功能挂进去而不互相挤垮。

## 1 · 五条设计原则（脊柱）

1. **时间线是脊柱。** 聊天消息、CLI 输出、浏览器动作、DesignAction、审查、记忆写入都是 `SessionEvent`。界面只是它的不同透镜。不引入第二套 session/store（呼应 AGENTS 规则 13/19）。
2. **是 Surface，不是 Page。** 全局只有少数几个常驻 Surface；功能"挂进" Surface，而不是新开顶层页面。新功能默认问："它挂在哪个 Surface 的哪个槽"，而不是"它是第几个 tab"。
3. **人机对等(agent-native parity)。** 每个人类操作都有等价 `DesignAction`/工具调用；反过来，agent 的动作必须用**和人类完全相同的**选区 chips、动作流、权限卡、证据包来呈现。人和 agent 是同一画面的共编者，界面用 actor 徽章标注"谁做的"。
4. **能力门禁是一等 UI 状态。** 每个 Surface 声明可编辑范围：远程网页=只选择/标注/截图/证据；Fleet/Open Design artifact=可编辑；未接后端=可见但 disabled 且给真实原因。永不做假按钮（呼应 §19 与 AGENTS 规则 19/21）。
5. **渐进披露。** 默认是"会话优先"的简单态(新手无感)；强力 Surface(Stage/Inspector/Context) 按需打开并按 session 记忆；紧凑/窄屏退化为一次一个 Surface，会话永远可达。

## 2 · 顶层布局：Workbench 三区 + 两条 Rail

```
┌───────┬───────────────────────────┬───────────────────────────┬──────────────┐
│       │                           │  STAGE (工作面，可切模式)  │  INSPECTOR   │
│ NAV   │     CONVERSATION          │  ┌─────────────────────┐  │  (选区驱动)  │
│ RAIL  │     (会话 = 时间线脊柱)    │  │ 模式: 浏览器▾ Artifact │  │ Inspect      │
│       │                           │  │      Figma  Preview  │  │ Comment      │
│ 会话  │  模型/CLI 选择 · 选项徽章  │  │                      │  │ Library      │
│ 智能体│  消息流(人/agent/工具)     │  │  [docked BrowserPane  │  │ Actions      │
│ 源/技能│  权限卡 · artifact 按钮   │  │   = 预留矩形,原生视图]│  │ Handoff      │
│ 设置  │                           │  │                      │  │              │
│       │  输入区(@Agent /Skill 附件)│  │  工具栏:选择 框选 标注 │  │ ─ Context ─  │
│       │                           │  │  Comment AI 保存证据  │  │ Usage/成本   │
│       │                           │  └─────────────────────┘  │ ProjectPack  │
│       │                           │                           │ 外部审查     │
├───────┴───────────────────────────┴───────────────────────────┴──────────────┤
│  ACTION TICKER  时间线动作流: [人] set_style div.card · [agentA] annotate ×3 · 权限:写文件? │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **NAV RAIL（左）**：沿用 craft navigator——会话/源/技能/设置，外加 **"在工作的智能体"** 名册(多 Agent)。窄屏可收起。
- **CONVERSATION（中）**：始终在场的脊柱。承载对话、模型/CLI 选择、active-options 徽章、权限/凭据卡、artifact 动作按钮、消息流(它本身就是人类可读的时间线)。这是新手唯一需要看的列。
- **STAGE（右中）**：可切换的工作面，一次显示一种 **Stage 模式**，但各模式状态独立记忆。第一落点是 **Browser**（docked），Artifact Studio 是在 artifact 上操作时打开的第二层。
- **INSPECTOR + CONTEXT（右）**：选区驱动的统一检查器(Inspect/Comment/Library/Actions/Handoff) + Context 透镜(用量/打包/审查)。它是 Browser 选区与 Artifact 选区**共用**的——这是统一的关键。
- **ACTION TICKER（底，可收起）**：实时动作/工具/权限流，带 actor 徽章，是"共编在场感"的所在。点动作 → 跳转/回放。

关键取舍：因为浏览器停靠走 **re-parent 子窗口**（原生视图浮在 React 之上、不裁剪），Inspector/Context 必须是 Stage **旁边的兄弟列**，绝不浮在浏览器矩形之上；Stage:Browser 区是 React 留空、原生视图覆盖的"**预留矩形**"。需要弹窗/菜单盖住浏览器时，先 hide/detach 原生视图。这条约束是布局的硬边界，不是审美选择。

## 3 · 五个常驻 Surface 的职责

| Surface | 职责 | 承载的愿景功能 |
|---|---|---|
| Conversation | 对话 + 人类可读时间线 + 入口 | API/CLI 对话、模型/effort、技能/命令、附件、artifact 检测按钮、权限/凭据、source 激活 |
| Stage | "动手"的工作面(原生/可编辑) | Browser(真实网页+标注)、Artifact Studio(编辑 artifact)、Figma/Stitch、Preview/Files |
| Inspector | 选区驱动的精修 + 证据 + 交接 | Inspect(文本/布局/外观/效果/字体/颜色)、Comment(证据/Comment AI/保存证据)、Library(媒体/组件/模板/字体/色板/动效)、Actions(DesignAction 流)、Handoff(导出/Figma/Stitch) |
| Context | 成本/用量/审查透镜 | Usage/Token Report、ProjectPack 打包、外部 AI 审查、压缩前后 |
| Action Ticker | 共编在场 + 回放 | 人/agent 动作流、权限事件、selection 变更、跳转/回放、多 Agent 并发分流 |

设计纪律：**新功能必须落进上面某个 Surface 的某个槽**。如果一个功能"无处可挂"，要么是 Surface 划分错了，要么这个功能其实是另一个功能的状态。不允许为单功能新开顶层页。

## 4 · Stage 模式：浏览器优先，Artifact Studio 第二层

Stage 顶部是模式切换条(像浏览器标签，但切的是工作面)：

Stage 是"一个画布多种模式"——模式由"在做什么"决定，不是"开了哪个 app"。所有模式共用同一选区模型，喂同一个 Inspector，进同一条 timeline。目标态全集如下（`阶段` 列对齐 `docs/01` M0–M3，标明建造顺序，不是一起做）：

| Stage 模式 | 服务场景 | 何时出现 | 能力门禁 | 工具栏 | 阶段 |
|---|---|---|---|---|---|
| **Browser**(第一落点) | 通用·设计·审查 | 用户开浏览器 / agent 用 `browser_tool` / 外部审查提交 | 远程网页=只读 DOM：选择/框选/标注/截图/证据/发给 AI；**不可改远程源站** | 导航 + 选择/框选/标注/Comment AI/保存证据 | M0 |
| **Design Canvas / Artifact Studio**(第二层) | 软件·AIGC 分镜图 | 在 Fleet/Open Design artifact 或本地 editable preview 上操作 | 可编辑：非破坏性 patch | 浏览/选择/编辑/标注 + Inspector 联动 | M1 |
| **Code** | 软件开发 | 打开代码文件/diff | 可编辑：走 craft file diff + permission | 编辑/diff/符号选择 + Inspector(符号属性) | M2 |
| **Timeline**(媒体/编辑时间线) | 内容创作·AIGC | 编辑动画/视频/音频/字幕 | 可编辑：原生轨道/片段操作，经动作信封进入 timeline | 播放头/轨道/关键帧/片段/速度/转场 | M2 |
| **Board / Compositor** | AIGC·分镜·片段拼合 | 编排分镜、拼合片段 | 可编辑：原生格/片段重排，经动作信封进入 timeline | 分镜格/排序/片段拖拽/批量重生成 | M2 |
| **Figma / Stitch** | 设计交接 | 交接/导入 | 官方 API + 权限；席位受限显式展示 | read context / write canvas(授权后) | M3 |
| **Preview / Files** | 通用 | 看文件/产物 | 只读 | — | M1 |

> **建造顺序铁律**：协作/权限/资产底座先行，Canvas/AIGC/网页文档形成 M1 创作闭环，Timeline/Board/Compositor 在 M2 进入主线。专业工作面可以有自己的布局和原生引擎，但不能另起 session、资产库、权限或 Agent 真相。

要点：

- **Browser 是设计工作流的第一块画布**，承接 `docs/06` 路线；普通网页严格降级为"选择+注释+截图+证据包+发给 AI"，证据进 timeline，agent 引用。
- **Artifact Studio 是第二层**：只有当对象是可编辑 artifact/preview 时才进入。它不是入口，是"在 artifact 上深编辑"时的 Stage 模式。新实现必须从 `DesignAction -> DesignPatch -> SessionEvent` 建后端闭环。
- 两种 Stage 共用**同一套 `DesignSelection` / `DesignAction` / Inspector**——浏览器里框选三张卡片，和 artifact 里框选三张卡片，进的是同一个检查器、同一条动作流。这就是"不孤岛"。

## 5 · Inspector：被两种 Stage 共用的统一检查器

Inspector 由"当前选区(单/多/框选 set)"驱动，与选区来自 Browser 还是 Artifact 无关：

- **Inspect**：文本/布局/外观/效果 + 字体(族/字重/字号/行高/字距)/颜色(取色器+token)/基础变换。远程网页时整组只读(显示计算样式但不可写)，artifact 时可写。
- **Comment**：单/多选证据摘要、截图区域、注释、**Comment AI**(把选区证据带进下一条消息)、**保存证据**(生成本地 `DesignAction`,状态 `pending_backend`，不谎称写入 timeline)。
- **Library**：媒体/组件/模板/字体/色板/动效；拖到 Stage。来源、许可证、hash、版本和回滚由后端 asset 服务记录，UI 只展示已授权资产与可执行动作。
- **Actions**：人和 agent 的 `DesignAction` 流，带 actor/surface/operation/status(preview_only/pending_backend/committed)。这是 agent-native 的可视化窗口。
- **Handoff**：导出 HTML/CSS、让 AI 整理实现、Figma、Stitch；未接后端 disabled。

## 5.5 · 统一输入与项目类型（核心交互）

整个创作台只有**一个主输入框**（在 Conversation 底部），用户不需要为不同场景切换不同输入区。它按"当前选区 + 当前 Stage 模式 + 当前项目类型 + 上下文/记忆"路由（完整路由表见 `docs/02` 第 4 节）：

```
用户一句话 ──▶ 路由器(读 选区/Stage模式/项目类型/记忆)
                    │
   ┌────────────────┼────────────────┬─────────────────┬──────────────┐
   ▼                ▼                ▼                 ▼              ▼
DesignAction     时间线 op        代码 patch        审查中心        合成/导出
(改样式/分镜)    (调速/关键帧)    (改函数/文件)     (项目审查)      (拼片段/上线)
   └──────────── 全部进同一条 session timeline，带 actor，可授权可回放可回滚 ──┘
```

要点：
- **一个输入框，多种结果**："把这个按钮调大""把这段动画变快""把这个分镜改成夜景""审查这个项目""把这几个片段合成"——同一个框，路由按上下文决定交给谁。
- **统一输入 = DesignAction 的一体两面**：人打字和 Agent 调结构化工具，进同一条路由、同一条 timeline、同一套权限/回滚。这让输入天然 agent-native。
- **诚实兜底**：路由解析不出明确目标时，回到 Conversation 让用户澄清，不猜危险动作。
- **项目类型配置工作台**：新建/打开项目时选类型（软件 / 内容创作 / AIGC / 混合）。项目类型决定**启用哪些 Stage 模式、哪些 Agent（代码/设计/审查/测试/合成）、哪些素材库、哪些导出目标**——同一套 Surface，不同配置，不为某场景新做一套 UI。
- **NAV Rail 顶部是项目切换**：每个项目带自己的时间线脊柱、素材库、记忆分区（`docs/05`）、权限档。

## 7 · 人机协作模型（本设计的灵魂）

三种角色，同一套 Surface：

- **人类用**：鼠标驱动 Stage(导航/选择/框选/改属性/标注)，在 Conversation 说话，审批权限卡。
- **Agent 用**：用工具(`browser_tool`/未来 `design_tool`) 驱动**同一个 Stage**，产出**同一种** `DesignSelection`/`DesignAction`；界面用 agent 配色的"选区/光标"呈现它的操作，把动作流推进 Action Ticker，把高风险动作(写文件/导航到登录/外发)路由到 Conversation 的权限卡。
- **共编**：选区 chips、动作流、证据包**不分人/agent**——这正是"共编"而非"两个工具"的根本。

共编的关键交互(必须在 UI 里有):

| 交互 | 含义 |
|---|---|
| Actor 徽章 | 每条动作/选区/消息标 `user` / `agentA(runtime)`，多 Agent 用不同色 |
| Presence | Stage 上显示 agent 当前选区/正在编辑的元素(共编在场感) |
| Take control / Follow / Hand off | 人可暂停 agent、让镜头跟随 agent、或把当前 Stage 交给 agent 继续 |
| 权限卡 | agent 的危险动作进 Conversation 审批，结果回写 timeline(呼应 AGENTS 规则 16) |
| 回放 | 任一 `DesignAction`/工具调用可在 Action Ticker 点开跳转/回放(待后端 patch engine) |

## 8 · 能力门禁与诚实状态

UI 用统一的状态词汇，避免"看起来能用其实没接"：

| 状态 | 视觉 | 用在哪 |
|---|---|---|
| editable | 正常可交互 | Fleet/Open Design artifact、本地 preview |
| remote-readonly | 选区可标注、属性只读 | 远程网页 DOM |
| preview_only | 黄标 | 改了 iframe 预览但未落 patch |
| pending_backend | 蓝标"待后端" | Library、Figma/Stitch、保存证据未持久化 |
| committed | 绿标 | 后端 patch/timeline 落地后(暂无) |

## 9 · 关键人类工作流

1. **网页找灵感→局部改我自己的页**：Stage:Browser 打开参考站 → 框选三块 → 保存证据/Comment AI → 切到自己的 artifact(Stage:Artifact) → Inspector 批量改 → Handoff 让 AI 整理。
2. **AI 生成网页→直接微调**：Conversation 收到 artifact → 点"编辑" → Stage:Artifact → Inspect 改字体/色/圆角(即时预览) → Actions 看动作流 → 发下一条消息时设计上下文已带上。
3. **审查我的项目**：Context:ProjectPack 打包当前 diff → secret scan → 确认 → agent 用 Stage:Browser 提交到授权的 AI 站 → 回收合并成报告(真实/估算成本分开)。

## 9.5 · 三类创作场景端到端走查（同一套界面，不同配置）

证明"一个工作台不是三个 app"——三场景走同一条 Surface 闭环，只是 Stage 模式 / Agent / 库 / 导出不同（对照表见 `docs/02` 第 6 节）：

**A. 软件开发**：Conversation 说需求 → 设计 Agent 在 Stage:Canvas 出页面、用户在 Inspector 调样式/字体/色 → 代码 Agent 在 Stage:Code 实现前后端、走 file diff + permission → 测试 Agent 跑测试进 timeline → Context 打包 diff 做内部/外部审查 → Handoff 部署上线。统一输入全程："把这个表单改成两列""这个接口实现一下""审查并列出风险"。

**B. 内容创作（视频/动画）**：Conversation 给脚本 → 生成 Agent 出动画/素材进 Library → 用户在 Stage:Timeline 逐帧/关键帧调整、拖片段、配字幕音频 → "把这段变快""这里加转场"经统一输入路由成时间线 op → 版本对比预览 → Handoff 渲染导出 + 上传平台。媒体时间线的每次编辑都产生 DesignAction 落到会话时间线脊柱，可回放可回滚。

**C. AIGC（小说→短视频）**：Conversation 给小说/设定 → 文本 Agent 出剧本/分镜文本 → 设计 Agent 在 Stage:Canvas 出分镜图、用户在 Stage:Board 编排分镜格 → "把这个分镜改成夜景"路由给设计 Agent 重生成该格 → 生成 Agent 出短视频片段进 Library → Stage:Compositor 多选片段"合成一个作品" → Handoff 导出成片 + 上传。

三条都共用：项目容器、时间线脊柱、Inspector、Library、版本、导出、统一输入、Agent 协作、记忆分区、权限、token 账本。

## 10 · 关键 Agent 工作流

1. **agent 按指令改一组卡片**：agent 调 `design_tool` 选区 → 产生和人类一样的 selection set/Action(actor=agent) → 改样式走同一 patch 通道 → 危险操作弹权限卡 → 人在 Action Ticker 看到并可回滚。
2. **agent 做网页调研**：agent 用 `browser_tool` 在 Stage:Browser 导航/截图/取证 → 证据进 timeline → 人可 Follow 镜头、随时 Take control。
3. **agent 跑外部审查**：agent 在 Stage:Browser 用用户授权登录态提交 bundle → 每次外发前权限卡(目标站/包大小/secret/profile) → 结果归一成 ReviewReport。

## 11 · 响应式 / 紧凑 / 可达性

- 宽屏：Conversation + Stage + Inspector 三列并存。
- 中屏：Inspector 收成抽屉(选区时滑出)。
- 窄屏：一次一个 Surface，底部切换；Conversation 永远可回。
- 原生浏览器视图在窄屏/紧凑下必须能整体 detach 隐藏，避免遮挡。
- 键盘可达：模式切换、选择/框选/标注有快捷键；Action Ticker 可键盘浏览。

## 14 · 最难问题与设计对策

- **原生浏览器视图 z-order vs React 面板**(re-parent 子窗口浮在上层)：Inspector/Context 设为 Stage 的**兄弟列**而非浮层；Stage:Browser 是预留矩形；弹窗/菜单覆盖时 detach 视图。布局必须服从这条。
- **选区在响应式/SPA 下失稳**：选区生成即固化 provenance(selector/rect/dpr/viewport/scroll/截图时刻)；刷新后失效的选区降级为历史证据。
- **源码回写**：Inspector 显示 preview/pending/committed，UI 诚实；patch engine 由后端把 `DesignAction` 编译成最小 diff。
- **多 Agent 并发**：actor 配色 + Action Ticker 分流 + presence；权限/日志全程带 agentId(AGENTS 规则 15)。
- **信息过载**：渐进披露——默认只 Conversation；Stage/Inspector/Context/Ticker 全部按需 + 按 session 记忆 + 窄屏退化为单 Surface。

## 15 · 一句话总结

Fleet 不是把 12 个工具塞进一个壳，而是**一条共享时间线 + 五个常驻 Surface + 一套人机对等的动作模型**：人和 agent 在同一个 Stage 上、用同一套选区与 DesignAction、把结果写进同一条 timeline；浏览器是设计工作流的第一块画布，Artifact Studio 是在 artifact 上的第二层深编辑；任何没接后端的能力都诚实地 disabled，而不是假装完成。
