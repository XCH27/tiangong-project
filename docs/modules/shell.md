## Candidate data boundary, not yet a migration plan

The best working hypothesis is **Host → optional Project/folder → Conversation** for visible
navigation. Host identifies this device or one user-owned remote runtime. A Project refers to a
folder on a Host; a Conversation may be Project-bound or folderless. Installed capabilities belong
to a catalog, while each Conversation selects an effective suite from available Components, Skills
and MCPs. Project or user defaults may seed it. The accepted selection is captured at a turn
boundary and cannot itself grant file, network or OS permissions.

This is a recommendation from the source comparison, not a settled storage design. Craft currently
uses Workspace paths in Session, Project, Source, Skill and remote routing. Retain a compatibility
read path until an inventory proves where every old record appears, how two old Workspaces naming
the same folder remain distinct, how local/remote path identity works on Windows/macOS/Linux, and
how a disconnected host or unavailable suite is shown without data loss. Do not auto-merge or
delete records. The UI may eventually hide Workspace only after those proofs exist.
