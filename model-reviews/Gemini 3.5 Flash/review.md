# Fleet Technical Architecture & Design Review Report (Gemini 3.5 Flash)

This independent, clean-room audit report evaluates the core technical route selections, system architecture, security controls, and documentation design of the **Fleet** project. 

---

## 1. Executive Summary & Philosophy Audit

### 1.1 Product Positioning & Spine Unification
The decision to unify the codebase under the product name **Fleet** (built on the Craft Agents base) is highly correct. Treating the platform as a single "spine" (reusing the Craft shell, sessions, permissions, timeline, and SQLite DB) prevents the architectural fragmentation common in multi-agent desktop projects. 
*   **Verdict:** Strong Alignment. By avoiding the temptation to recreate a custom desktop IDE or chat shell, the project saves approximately 50% of bootstrap work.

### 1.2 "80/20" Creative Human-Agent Boundary
The philosophy that humans own the top 10% (creative strategy) and bottom 10% (safety guardrails/approvals), while agents run the middle 80% (production execution), is realistic and engineering-sound. However, the documentation lacks a concrete definition of how the bottom 10% safety rails prevent **user prompt fatigue** (e.g., if a worker spawns 50 consecutive L3 permission dialogs, the human will blindly click "approve").
*   **Key Suggestion:** The permissions and session systems must support **Batch Approval Envelopes** to group related transactions into a single human review dialog with integrated unified diffs.

## 2. Technical Route Selection Audits & Optimizations

### 2.1 App Server Daemon Architecture (WebSocket / RPC)
*   **Selection:** The CLI (`craft-cli`) and Electron GUI act as equal clients connecting to a long-running headless Bun Server via WebSocket.
*   **Crucial Security Gap:** Local WebSocket ports (e.g., `localhost:8080`) are accessible to any process or web page running on the user's computer. A malicious web script in a standard browser tab could connect to the unauthenticated Bun port and execute commands in the terminal.
    *   **Optimization:** A cryptographically secure workspace token must be generated by the Electron main process at boot and saved in a local, permission-restricted workspace file (`.fleet/session.lock`). The CLI and GUI clients must pass this token during the WebSocket connection handshake.
*   **Crucial Port Conflict Gap:** Hardcoding local ports (like `8080`) will fail if multiple users are on the same machine or if the user opens multiple separate workspaces.
    *   **Optimization:** On macOS/Linux, the Bun Server should bind to a **Unix Domain Socket** located inside the workspace directory (e.g., `.fleet/server.sock`). On Windows, it should use a **Named Pipe** (`\\.\pipe\fleet-<workspace-id>`). This eliminates port conflict bugs and enforces OS-level access control boundaries automatically.
*   **Single Writer Principle:** The SQLite database file must **only** be opened and written to by the Bun Server process. The Electron main process and CLI must never query or write to the SQLite file directly. This avoids SQLite database locking issues under concurrency.

### 2.2 Terminal & CLI Integration (PTY vs. Raw Spawn)
*   **Selection:** Spawning terminal processes and saving log outputs to timeline evidence.
*   **Engineering Audit:** Spawning shell tasks directly via standard child processes (`exec` / `spawn`) results in broken environment variables and blocks interactive shell inputs.
    *   **Optimization:** The platform must use **`node-pty`** in the Electron main/Bun daemon layer to create real pseudo-terminals. This captures stdout/stderr streams cleanly and handles shell configuration (`.zshrc`, `.bashrc`) exactly like a real terminal emulator.
*   **Rollback Boundary Definition:** Rolling back terminal executions is historically non-deterministic (e.g., rolling back `npm install` or `rm -rf`).
    *   **Optimization:** The specs must explicitly declare terminal commands as **irreversible (non-rollbackable) actions** unless they operate strictly on workspace-controlled files tracked by Git worktrees. The terminal spec (`M02`) should reject automatic rollbacks for general terminal commands and warn the user.

### 2.3 Graded Permissions (L0-L3) & Multi-Agent Seat Enforcement
*   **Selection:** `seats:create` assigns rigid roles/domains (`role:worker`, `domain:code`).
*   **Deadlock Risk:** If a code-agent (`domain:code`) needs to inspect an image file (`domain:media`) to write corresponding CSS, the rigid tag configuration will return `PERMISSION_DENIED`, halting the agent.
    *   **Optimization:** The Internal Action Registry must expose a L2 action **`seats:request_elevation`**. When blocked, the agent invokes this action to request temporary tags from the Lead or Human, providing an automated fallback pathway instead of crashing.

### 2.4 Canvas & Video Render Loop CPU Offloading
*   **Selection:** Canvas (OpenPencil) and Video (OpenCut with FFmpeg).
*   **Performance Risk:** Running heavy image processing and video clipping/rendering inside the Electron main process or Bun event loop will cause UI thread lockup.
    *   **Optimization:** All video operations (FFmpeg spawning) and large-scale Canvas frame processing must run in a low-priority queue (`nice` on macOS/Unix) and execute in decoupled background worker threads. Timeline progress updates (`video:progress`) must be throttled to a maximum of 1 message per 250ms to prevent network saturation of the WebSocket control plane.

## 3. Document Structure & Consistency Audits

### 3.1 Naming Discrepancies
*   **Finding:** The name `FleetBridge` is still referenced alongside `Craft Agents Bridge` in several spec files, causing minor conceptual confusion.
*   **Correction:** We must strictly unify this to **`FleetBridge`** or **`Fleet Bridge`** globally.

### 3.2 "Stop Criteria" Gaps in Wave Map
*   **Finding:** The W1 phase does not explicitly forbid worker agents from starting execution modules before M00 is completed.
*   **Correction:** Implement strict gate-locking statements inside `WAVE-MODULE-MAP.md` that physically block workers from checking out branch tasks for subsequent waves if previous wave stop criteria are unmet.

---

## 4. Summary of Suggested Concrete Next Actions

1.  **Deploy UDS / Named Pipes:** Replace port-based WebSocket routing with Unix Sockets/Named Pipes for local-first safety and workspace isolation.
2.  **Enforce Handshake Tokens:** Add secure token validation at Bun daemon startup to secure the WebSocket RPC port.
3.  **Specify Rollback Capabilities:** Formally document in `M02` and `M03` which actions support true rollback (Git-tracked workspace edits) vs which actions are destructive and irreversibly L3.
4.  **Batch Actions:** Add batch execution support to the hook pipelines to prevent prompt approval fatigue.
