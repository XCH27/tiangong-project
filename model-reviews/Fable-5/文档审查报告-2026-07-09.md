# 项目文档审查报告

日期:2026-07-09 | 审查范围:docs/ 全部活动文档、AGENTS.md、契约文件,并逐条与 app/ 真实代码核对

## 总体判断

理念层没有大问题:单一 spine + 各 surface 原生引擎、L0-L3 权限分级、契约冻结 + 波次门禁 + packet 隔离、四态 status、OWNER-VOICE 翻译层——这套设计自洽且成熟。

真正的问题在三类:**文档之间互相矛盾**(同一事实在多处记载已漂移)、**文档与 app/ 真实代码脱节**(大量"现有复用"引用的其实是 fleet-old 的文件)、**冻结契约三处版本不一致**(W0 门禁按它自己的定义其实没通过)。你还没动手写代码,正好先修这些——否则第一批 Worker Agent 会在预检和"Files To Inspect First"阶段集体卡死。

## P0 — 开工前必须修(会直接卡死 Worker)

### 1. W0 门禁按自身定义并未满足
AGENTS.md 的 W0 硬阻断条件要求 `protocol-stubs.md` 冻结 `SessionEvent`、`ActionInvocation`、**`AgentSeat`、`RuntimeLane`** 四个类型。实际 stubs 文件里只有 SessionEvent、ActorRef、ActionInvocation、WorkspaceFileLease、CanvasDocument——**没有 AgentSeat 和 RuntimeLane**。另外:
- PARALLEL-AGENT-OPERATING-MODEL 说 Bridge 的 `RuntimeLaneEvent`/`TeamContextSnapshot`/`LaneOutcome` "defined in protocol-stubs.md"——不存在。
- identity-tags 矩阵说 Seat 类型在 `protocol/agent-session.ts` "frozen at W0"——无此 stub。
- W1 packet 却要求 Seat 1 "matching protocol-stubs.md" 实现 AgentSeat/AgentSession。

**修法**:补齐这几个类型 stub 后再宣告 W0 通过,或修改门禁定义。现在的"W0 Done + SHA 证据"是形式通过、实质未过。

### 2. 同一契约三处版本漂移
- `docs/contracts/action-ids.md`:FROZEN **v1.2.0**,21 个 action id(含 file.move、canvas 全家桶、aigc.job_submit)。
- `app/packages/shared/src/protocol/internal-action.ts`:`CONTRACT_VERSION = '1.0.0'`,只有 **10 个 id**(无 file.move、无 aigc.job_submit,canvas 只有 node_update)。
- 而两边的规则都写着:改表必须**同一 commit** 同步 bump CONTRACT_VERSION。

**修法**:选一边为准,把另一边补齐到同版本,并在 W0 验证记录里重新留证。

### 3. 权限分级体系自相矛盾
- stubs 里 `ActionPermissionLevel` 只有 L0/L1/L2;代码里有 L0/L1/L2/**L3_destructive**;D12、M00、M12、M13 都在用"L3"。stub 缺 L3。
- L1 的定义是"必须返回 UndoHandle",但冻结表里 `aigc.job_submit` = L1 + undo not_supported;M06 的 browser.click/type、M09 的 video.export_clip 同样 L1 + 不可撤销;反过来 `workspace.rename` = L2_irreversible 却 undo supported。
- M08 spec 说 job_submit 的 undo handle 是 job_cancel,与冻结表"not_supported"直接矛盾。
- 冻结表"destructive=true ⇒ SupervisionRequest"的语义,按代码注释其实是 L3 的行为,和 L2 定义混在一起。

**修法**:把"风险等级"和"可撤销性"解耦成两个正交字段(risk tier × undo capability),L3 补进 stubs,然后逐行重审 action 表。

### 4. Packet 授权与冻结规则/所有权矩阵冲突
- W1 packet 允许 Worker 改 `protocol/internal-action.ts`、`protocol/session.ts`;W2 packet 允许改 `protocol/team-run.ts`、`protocol/usage.ts`——**全部落在"永远 Lead-owned"的 `protocol/*.ts` 冻结 glob 内**。
- packet 路径与 OWNERSHIP-MATRIX 系统性不一致:M02(matrix: `renderer/terminal/` + `main/terminal-host.ts` vs packet: `renderer/components/terminal/*` + `server-core/src/runtime/cli-launcher.ts`)、M03(matrix: `action-registry/` + `main/action-executor/` vs packet: `protocol/internal-action.ts` + `action-executors/*.ts`)、M05(matrix: `shared/src/library/` vs packet: `server-core/src/files/library.ts`)。且 `action-executors/*.ts` 通配与 M06-M09 各自拥有的 browser.ts/canvas.ts/aigc.ts/video.ts 重叠。

**修法**:以 OWNERSHIP-MATRIX 为单一事实源重写所有 packet 的 Allowed Files;protocol 改动只留"contract change request → Lead 执行"一条通道。

### 5. "现有代码复用"清单写的是 fleet-old,不是 app/
逐一核对结果:`cli-runtime.ts`、`team-run.ts`、`team.ts`、`subscription.ts`、`usage.ts`、`memory.ts`、`capability.ts`、`services/acp/`、`team-run-coordinator.ts`、`oss-sync.ts` 在 **app/ 里全部不存在**,但在 `源码参考/software/fleet-old` 里 **9/9 全部存在**。M02/M04/M10/M11/M12 的 "Files To Inspect First" 和 "Current App Reuse" 是对旧仓库写的。M03 声称复用的 "DesignAction envelope" 同样不存在。

**修法**:每个模块 spec 按当前 app/ 重新核对复用清单;明确列出"需从 fleet-old 移植"的协议/服务清单。另外,fleet-old 不在 REFERENCE-PROJECT-POLICY 的绿灯表里——按你们自己的政策,现在连自家旧代码都禁止复制,应补一行绿灯条目。

### 6. 工具链命令写错(pnpm vs bun)
仓库是 Bun workspaces(craft.sh 就是 bun 的包装)。但 PARALLEL-AGENT-OPERATING-MODEL 的 Completion Report 模板和 M06/M07/M08/M09 的 Validation Ladder 全写 `pnpm typecheck`、`pnpm test --filter <package>`(pnpm 专有语法)。**修法**:统一为 `./scripts/craft.sh run typecheck:all` 等真实可跑的命令。

### 7. M06 浏览器嵌入路线与基座相反
M06 SPEC 规定"使用 Electron `<webview>` tag"。但基座 `window-manager.ts:261` 明确写着 `webviewTag: false // Browser integration uses WebContentsView, not <webview>`,现有 BrowserPaneManager 就是 WebContentsView 路线;Electron 官方也长期不推荐 webview tag。M06 同时声称"Reuse existing BrowserPane"——两句话相互矛盾。**修法**:M06 改为延续 WebContentsView 架构(选区/标注 overlay 在主进程 attach 的 view 上做),删除 webview tag 方案。

### 8. "English-only" 规则与预检 Q4 形成死锁
AGENTS.md 说活动文档 English-only,但 PROJECT-DIRECTION §13、WAVE-MODULE-MAP 的 W1 执行顺序、三份 IMPLEMENTATION.md、整份 ARCHITECTURAL-COMPARISON 都是中文;packet 预检问题 4 要求确认"module spec 无中文字符"——Worker 严格执行会全部卡在 Q4 无法开工。**修法**:二选一——放宽为"英文为主、允许标注双语",或把上述文档翻译。别留死锁。

### 19. ARCHITECTURAL-COMPARISON 可信度问题
这份"客观决策依据"里各产品的版本号/日期无法核实;"Antigravity 2.0"条目描述的特性(Bun 本地容器、Action 注册表、role/domain 权限矩阵、Timeline 审计)与**本项目自身设计雷同**,疑似生成时把自家方案混进了虚构竞品;"Claude 桌面本质是 Shell Out 调用 Claude Code CLI"作为一般性断言不准确;多处中英夹杂("机制 of 深度剖析"、"被调度 and 工作"、"网络 and 云端"、"邮件框");8 周/16 周工作量估算无依据。

**关键点**:选型结论(App Server 模式、保留 Electron+Bun)其实不需要这张表支撑——`packages/server`(Bun daemon)+ `apps/cli`(MessageEnvelope WS RPC 客户端)+ Electron 三件套在基座里**已真实存在且工作**,这是最硬的论据。建议给该文档加"生成内容、未逐条核实、仅作背景"横幅,把 §13 的论证改写为基于自家代码事实。

### 20. 所有权嵌套重叠未定义优先级

## 最后一条系统性建议

最大的风险不是设计,而是**文档规模 vs 维护能力**:14 个模块 × 多份控制面文档,在还没写一行产品代码的今天已出现 20+ 处漂移。建议:

1. **收缩活动集**:只保留 W1 真正需要的最小文档集(START-HERE、DECISIONS-LEDGER、W1 packet、M00/M03 spec、3 份 contracts)为"binding",其余全部标 `draft`,进波次前再逐份激活并核对。
2. **一致性检查自动化**:路径存在性(`test -e`)、pnpm/bun 命令、重复节号、版本号一致(action-ids.md vs CONTRACT_VERSION)、wave 状态单一来源——都可以写进一个 `docs-verify.sh`,每次 Lead 会话结束跑一遍。这比任何"记得同步"的纪律都可靠。
